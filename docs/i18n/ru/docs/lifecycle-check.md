# Воспроизводимая проверка жизненного цикла

`tooling/run-lifecycle-check.py` передаёт наблюдения цели, расхода и дочерних сессий закреплённому кандидату. Фактические наблюдения получает главный агент из среды. Храните сессию и входные данные закрыто, вне Git. Писать в данные сессии должен один агент.

<a name="prepare-before-measuring"></a>

## Подготовка до замера

Соберите кандидат и сохраните принятый внешний хеш. `prepare` проверяет пакет и записывает новую сессию, не запуская кандидат или монитор. Закончите подготовку до первого фактического замера расхода.

```powershell
python -X utf8 -B tooling/run-lifecycle-check.py prepare --candidate C:/build/agent-workflow-v1-1/scripts/candidate.py --manifest C:/build/agent-workflow-v1-1/manifest.json --manifest-sha256 PRESERVED_SHA256 --version 1.1 --project C:/project --run-id check-1 --session C:/private/check-1.json
```

`PRESERVED_SHA256` берётся из принятой квитанции сборки. Укажите существующий проект и новый файл сессии. После изменения пакета не привязывайте прежнюю сессию к другому хешу.

<a name="host-input-object"></a>

## Входные данные среды

`run`, `observe`, `resume`, `close` и `timed-test` принимают JSON-объект через `--input`.

| Поле | Содержимое |
| --- | --- |
| `activation` | Только первый `run`. Полный типизированный ввод кандидата для `bind-active-goal`, включая `native_binding`, соответствующее `app_goal_observation`, цель, интерпретацию, проверку процедуры, наблюдавшиеся модели и уровни рассуждения, ограничение мест, реальный перечень сессий и время наблюдения. |
| `app_goal_observation` | Актуальное наблюдение `get_goal` с идентификаторами цели и чата, текстом цели, временем создания и статусом, полем `source_kind: get_goal`, фактической ссылкой на источник и `observed_at`. Укажите подлинный `updated_at`, если доступен. |
| `usage` | Поля `source`, `sourceId`, `observedAt` и `result` из [штатных квитанций расхода](../skills/agent-workflow-v1-1/references/native-usage.md). Оставьте только требуемые окна. |
| `inventory` | Фактические текущие идентификаторы и статусы дочерних агентов. Используйте `[]` только при их отсутствии. |
| `checkpoint_files` | Относительные изменённые, добавленные и удалённые пути для восстановления, включая файлы главного агента. Ядро также добавляет пути, назначенные задачам. |
| `writers_quiescent` | `true` только после наблюдения, что все агенты закончили писать. Инструмент не может получить это наблюдение сам. |
| `next_action` | Конкретный следующий шаг после возобновления или нормального завершения. |
| `weekly_exception` | Необязательно для первого `run`. Действительная цитата `exact_quote` и ограниченный срок Unix `valid_until`. По умолчанию исключения нет. |
| `resume` | Необязательный полный ввод кандидата для возобновления. Без него инструмент пробует `usage_recovery: true` только после зафиксированного истечения срока. Остановка по квоте или пользователем сохраняет свои требования. |

Если штатный API не даёт отдельного идентификатора цели, используйте идентификатор, однозначно полученный из имеющихся данных, например `threadId:createdAt`. Укажите, что он производный. См. [эксплуатацию](../skills/agent-workflow-v1-1/references/operations.md) и [команды](../skills/agent-workflow-v1-1/references/commands.md) для типизированных форматов.

<a name="run-refresh-and-close"></a>

## Запуск, обновление и завершение

```powershell
python -X utf8 -B tooling/run-lifecycle-check.py run --session C:/private/check-1.json --input C:/private/initial-observation.json
python -X utf8 -B tooling/run-lifecycle-check.py observe --session C:/private/check-1.json --input C:/private/new-observation.json
python -X utf8 -B tooling/run-lifecycle-check.py close --session C:/private/check-1.json --input C:/private/final-observation.json
```

Записывайте фактическое время наблюдения сразу после штатного вызова. Инструмент проверяет `status.at == usage.observedAt`, идентификатор принадлежащего запуску процесса, эпоху, сигнал активности, замер и срок работы. `observe` также продлевает разрешение на работу. `refresh_by` предлагает более раннее обновление, не меняя фактического срока.

При `CHECKPOINT_SOON` проверьте контрольную точку готовой работы. Поддерживайте `checkpoint_files` в актуальном состоянии. Для нормального `close` нужны актуальный мониторинг, проверенный снимок, статус завершения и наблюдаемый выход процесса. В обычной работе SAVE не вызывается искусственно.

Первый `run` с `weekly_exception` устанавливает временное правило монитора и до активации возвращает `NEED_POLICY_OBSERVATION`. Получите новые наблюдения цели и расхода, затем повторите запуск той же сессии. Оставьте прежним исходное время каждой ранее полученной квитанции.

<a name="halt-and-resume-after-expiry"></a>

## Остановка и возобновление после истечения срока

При запросе SAVE команда `observe` выполняет остановку, снимок и окончательную остановку, затем возвращает `NEED_POST_HALT_OBSERVATION`. После неё получите новые наблюдения цели, расхода и списка сессий.

```powershell
python -X utf8 -B tooling/run-lifecycle-check.py resume --session C:/private/check-1.json --input C:/private/after-halt-observation.json
```

Ядро использует наблюдаемую причину монитора. Для технического возобновления нужны та же разрешённая активная цель, неизменные файлы и контрольная точка, свежие подтверждения после остановки и проверенный выход своего процесса. Для квоты, раннего резерва и явной остановки действуют применимые правила продолжения. Инструмент не переводит цель Codex в paused, blocked или active.

Если первая активация не удалась, сессия хранит хеш попытки запуска кандидата. Повторяйте тот же `run` с новыми подтверждениями только при соблюдении условий повтора. Изменённая сессия не принимается как подтверждение. Завершённые попытки и попытки с неясным исходом автоматически не повторяются.

<a name="run-a-timed-diagnosis-only-when-selected"></a>

## Диагностика времени по явному запросу

До события подготовьте исправный процесс. Используйте `timed-test` только для явно запрошенной диагностики. JSON события содержит `event_id`, `goal_id`, `thread_id`, `source_id`, `event_at` и `observed_at` из фактического штатного наблюдения.

```powershell
python -X utf8 -B tooling/run-lifecycle-check.py timed-test --session C:/private/check-1.json --input C:/private/current-observation.json --event-input C:/private/native-event.json --delay-seconds 10 --tolerance-seconds 1
```

Запоздавшее событие даёт `INVALID_TIMING`. `SAVE_REQUEST_ON_TIME` означает, что запрос SAVE уложился в допустимое время. Для штатной паузы нужны отдельные данные среды, поэтому инструмент сохраняет `native_pause_verified: false` и `native_paused_at: null`. Полная двухэтапная проверка на действующей системе наблюдает активное состояние, затем остановленное и снова активное после фактического разрешённого продолжения той же цели и запуска. Синтетическое время проверяет только логику.
