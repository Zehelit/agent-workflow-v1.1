# Штатные квитанции измерения расхода

Применяйте этот порядок только в явно разрешённом и включённом запуске AGWF. Текущий явный вызов требует запуска в согласованном объёме. Если создавать цель Codex запрещено, используйте ручной мониторинг из [руководства по эксплуатации](operations.md). Обновление пакета, обсуждение навыка и публикация данных сами по себе не включают выключенный рабочий процесс.

Главный агент вызывает `mcp__codex_app__get_usage_limits` по существующему соединению Codex. Python не открывает второй сервер приложения, не выбирает другую CLI, не читает файлы авторизации, не подключается к частным транспортам и не вызывает модели. Фоновый процесс следит за предоставленными квитанциями и сроком их действия. На границах работы инструмент среды по-прежнему вызывает главный агент.

Из фактического результата инструмента подготовьте закрытый входной JSON.

```json
{
  "source": "mcp__codex_app__get_usage_limits",
  "sourceId": "actual-tool-call-receipt-id",
  "observedAt": 1800000000,
  "result": {
    "rateLimits": {
      "limitId": "codex",
      "primary": {"usedPercent": 25, "windowDurationMins": 300, "resetsAt": 1800010000},
      "secondary": {"usedPercent": 30, "windowDurationMins": 10080, "resetsAt": 1800600000}
    }
  }
}
```

Числа приведены для примера. Сохраните фактическое время наблюдения, идентификатор квитанции и значения. Не выдумывайте их и не заменяйте время наблюдения временем записи файла. Если реальный результат содержит несколько групп лимитов, предпочтителен `rateLimitsByLimitId.codex`. Таблица без Codex отклоняется. Программа не переходит молча к другой группе. Обязательны длительности и время сброса обоих окон. В закрытые входные данные переносите только необходимые поля лимитов. Данные аккаунта, профиля и кредитов не нужны. Опубликованный `watcher/usage-source.json` содержит только разрешённые поля окон, идентификатор и время наблюдения, идентификатор источника и привязку к запуску и эпохе.

`workflow activate --input AUTH.json --usage-input USAGE.json` и `bind-active-goal` проверяют разрешение до запуска процесса. Для `resume` также нужна новая квитанция через `--usage-input`. Квитанция прежней эпохи не подходит. Ручной `watcher start --usage-input USAGE.json` проходит те же предварительные проверки. При отсутствии или истечении срока квитанции запуск отклоняется до создания процесса.

Во время работы публикуйте новый замер через `watcher ingest --usage-input USAGE.json` или опцию `--usage-input` команды рабочего процесса или координации. `ingest` не активирует рабочий процесс, не запускает монитор, не продлевает разрешение и не снимает зафиксированный SAVE. При новом файле источника оценка начинается без ожидания прежнего срока. Пока процесс читает источник, статус может кратко показывать прежнюю оценку. До ответственного назначения дождитесь актуального статуса, подтверждающего исправность.

Главный агент обновляет реальный замер до адаптивного срока, не более 300 секунд, а около порогов или при быстром расходе — раньше. Повторное чтение старого файла не выдаётся за новый замер. Если агент не может получить свежие данные, процесс повторяет проверку один раз и фиксирует SAVE_AND_STOP. После остановки с причиной `usage_receipt_expired` можно возобновиться в той же уже разрешённой активной цели через `workflow resume` и `usage_recovery: true`. См. [техническое возобновление](operations.md#expired-telemetry-recovery-under-existing-authority). Новые данные сами по себе не снимают остановку. Проверяемое возобновление по этому пути не требует повторного сообщения пользователя. Для реальной квоты и явной остановки пользователем действуют их правила продолжения. Обновляйте данные в подходящие моменты с запасом для следующего вызова. Указанный срок не является рекомендуемым временем ожидания. Не прерываемые длительные вызовы ограничивают возможность измерять расход. Самостоятельный доступ фонового процесса к штатному инструменту не предусмотрен.

Неверный формат, неправильные запуск или эпоха, будущие и просроченные наблюдения, обратный ход времени и изменённые повторы отклоняются. Повторная публикация тождественной квитанции не изменяет состояние. Как и у других штатных квитанций, время и источник указывает вызывающая сторона. Одна структура JSON не удостоверяет поставщика. Храните сырые подтверждения в закрытом месте и не принимайте произвольную метку источника за независимое подтверждение.

Ошибки замера показывают допустимый `diagnosticCode` и класс ошибки в замере и статусе, а в `watcher/diagnostics.json` хранится до 20 структурированных записей. Текст исключений, данные авторизации и произвольное содержимое инструментов не включаются. При непредвиденном сбое процесса Python остаётся локальный `worker-stderr.log`. stderr дочернего сервера больше не отбрасывается, поскольку сервер не запускается.

Полная проверка пакета выполняется для каждой команды кандидата и каждой оценки процесса, в том числе при новых входных данных. Сигнал активности проверяет только данные управления запуском и эпохой и публикует состояние. Он не повторяет обход и хеширование полного пакета. Изменённая зависимость будет отклонена при следующем замере или команде. На обнаружение каждого изменения при каждом сигнале рассчитывать нельзя.

Модульные тесты охватывают фактическую запись и чтение файлов квитанций, строгий JSON, срок действия, повторы, идентичность, пороги, ограниченную диагностику и отсутствие запуска процессов на пути замера. Эти тесты не заменяют проверку Remote на действующей системе. Оставляйте установленный процесс выключенным до его явного включения пользователем. Для обслуживания не запускайте действующий AGWF лишь ради видимости такой проверки.
