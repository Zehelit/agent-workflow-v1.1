# 運用

Python 3.11 以上を使います。依存関係は標準ライブラリだけです。`python -X utf8 -B scripts/candidate.py --help` でコマンドを確認できます。開始前に [ランタイムのひも付け](coexistence.md) を読み、外部のビルド記録にあるマニフェストの SHA を保存します。`python` が使えない場合は、ホストに同梱された Python を用います。コマンドは `--input path` または標準入力から JSON を読みます。状態の保存先は `<project>/.agent-workflow-v1-1/runs/<run-id>/state.json` です。チェックポイント、ロック、一時データ、監視プロセスの所有情報、調整のジャーナルもこの実行専用の名前空間に置き、書き込むのはメインの調整役だけです。ファイル、テスト成果物、スナップショットを通常のプロンプト入力にはしません。

<a name="start-and-dispatch"></a>

## 起動と割り当て

明示的に呼び出された場合は、準備や小さな作業でも、本格的な作業に入る前に同じターンで起動します。この指示書を読み込むだけでは足りません。ネイティブゴールを作成する権限がなければ、手動の監視で起動します。ゴールを作り上げたり、ひも付けの証跡を捏造したりしてはいけません。スキルについての話し合いや保守の依頼は、中止した割り当ての再開には当たりません。

ワークフローを有効化しない作業では、新しい実行 ID を選び、固定済みの候補パッケージで `watcher start --usage-input USAGE.json` を実行します。起動するのは監視のみで、ワークフロー状態は有効化せず、エージェントの割り当て権限も付与しません。`watcher status` で、この実行とエポックに対して新しく正常なサンプルと所有ワーカーの稼働が確認できるか、拒否が報告されるまで確認します。後続の実測値には `watcher ingest`、作業の区切りでのリース更新には `watcher renew` を使います。終わったら `watcher stop` を実行し、ワーカーの終了を確認します。条件が一致する正常な既存実行は再利用できます。停止済みの実行には、認められた再開と新しいエポックの手順、およびすべての復旧確認が必要です。ワーカーの重複起動で停止を回避してはいけません。作業前に観測した起動結果を報告します。起動に失敗したり `SAVE_AND_STOP` が要求されたりしたら、理由を報告し、本格作業は保留します。

有効化や再開の前に [ネイティブ使用量の観測記録](native-usage.md) を確認します。メインエージェントは既存の `mcp__codex_app__get_usage_limits` で取得した現在の実測値を `--usage-input` で渡します。バックグラウンドの監視はこの記録を読みます。Codex app-server を起動せず、ネイティブツールを自分で呼び出すこともできません。状況に応じた期限までに新しい実測値を取得します。記録を再利用しても鮮度は回復しません。記録がない、期限切れ、再送、実行 ID の不一致のいずれでも作業を止めます。手動で監視を始めた場合にも更新は必要です。`watcher ingest --usage-input PATH` はデータを反映するだけで、ワーカーの起動や AGWF の再有効化は行いません。

1. `validate` で定義を検証します。`activate` には `objective`、後述する型付きの権限証跡、`models`（観測したモデル別の推論強度一覧）、`slot_limit`（メインも数える稼働枠）、`inventory`（実際の子エージェントの ID と状態）、`observed_at`（Unix 時刻）を渡します。`session_limit` は任意です。利用できる機能の証跡を作り上げてはいけません。有効化はメインチャットのモデル設定を割り当てたり報告したりしません。
2. 固定済みの候補パッケージは、許可された `activate`／`bind-active-goal` の間に内部の監視プロセスを起動し、アクティブ状態を確定する前に最初の正常なサンプルを確認します。有効な `resume` の後は新しいエポックを開始します。稼働中のワークフローまたは調整のコマンドで 600 秒のリースを更新します。長めの作業の区切りでは `workflow status` を呼び出し、更新と状態確認を行います。リースが切れたり計測が正常でなくなったりすると新しい作業を拒否しますが、復旧コマンドは使えます。`complete`／`halt` は停止を要求し、ワーカーの実際の終了を確認します。手動の `watcher start/status/renew/stop` は診断や有効化されたワークフロー外の作業を対象とし、新しい実行 ID を使います。明示的な選択時は、適切な起動手順の実行と確認をメインエージェントが担います。Codex に起動フックはインストールされません。古い計測と復旧には、固定された内部の監視担当の方針を適用します。計測処理はモデルを呼び出さず、現在のチャットを制御しません。通常の利用枠確認にエージェントは起動しません。`usage-due` は `REUSE_MEASUREMENT` または `READ_USAGE` を返します。本格作業や並行作業の前は `substantial_work: true` で新しいツール計測を要求します。`usage` には `observed_at` と実ツールの生の `rateLimits` を渡します。両方の枠が必要です。不明な計測は一度だけ再試行し、その後は復旧に進みます。返される期限は、残りがそれぞれ 40% 超、25% 超、20% 超、20% 以下で 300／120／60／30 秒です。枠ごとの観測された減少率から 20% までの推定時間を求め、その 4 分の 1 がこれより短ければ期限を短縮します。リセットや古いサンプルからは減少率を求めません。残り 25% 以下、または推定で 10 分以下なら `CHECKPOINT_SOON` に従い、完了済みの作業のチェックポイントを検証します。毎メッセージで更新するのではなく、書き込みのまとまりが終わった時点で更新します。残り 20% 以下、または 20% まで残り 120 秒以下と推定される場合は `SAVE_AND_STOP` が割り当てを止め、早めに復旧に入ります。`prepare` は期限切れの計測を拒否します。待機中にポーリングは行いません。中断できない呼び出しや他のチャットによる急な消費を推定値で防げるとは限りません。
3. `task` には `id`、`role`、`objective`、`file_inputs`、`context_refs`、`review_targets`、`criteria`、`writes`（削除対象も含む正確なプロジェクト相対ファイルパス）、`depends_on`、`independent_review`（真偽値）を渡します。読み取り専用の作業では書き込み対象を空にします。ディレクトリを一括で書き込み対象にはできません。各割り当ての前に `inventory` で子エージェントの実際の状態を更新します。
4. `prepare` にはタスクの `id` を渡し、`effort` と固定済みの `current_context` は任意です。モデル、使用量、稼働枠、依存、ファイルハッシュを確認し、枠を確保して、`fork_turns: none` を含む実際の `collaboration.spawn_agent` の引数を返します。メッセージには割り当てた役割専用の `SKILL.md` と `MEMORY.md` が入ります。文書がないか空なら読み込みを拒否します。すべての文書はパッケージマニフェストに含まれます。準備した引数をそのまま使って呼び出してください。その後 `record` には `id`、`session_id`、`submitted_arguments`、`receipt`（実際のツール結果）を渡します。観測したメタデータに基づく `effective_model`／`effective_effort` は任意です。呼び出しが失敗した場合や結果が不明な場合は、`dispatch_failed` に `certain_not_started` を含めて記録します。セッションの有無が不明なら、実際の一覧で照合するまで追加作業を止めます。状況を確かめずに起動を再試行してはいけません。
5. `finish` には `id`、`accepted`、`evidence` と、独立レビューが必要な場合は `review_task` を渡します。まず `inventory` でセッションが idle、stopped、done のいずれかであることを観測します。書き込み担当が動いている間は所有を解除しません。レビューでは verifier の `review_targets` に対象タスクの ID とリビジョンを指定します。生成側の作業は止まっていても、レビュー完了まで受け入れは保留されます。レビューの間、成果物のハッシュは変わってはいけません。拒否された作業は拒否済みのまま保持し、原因を解決してから新しいタスクを作ります。`cancel` は `id` と `reason` を受け取り、準備された一度も割り当てていないタスクを解除します。メインの調整役は統合前にユーザーの編集を確認します。結果の分からない外部操作は、再試行する前に実際の状態と突き合わせます。

ワークフローの役割に使えるモデルは `gpt-6.1-sol`、`gpt-6-astra`、`gpt-6.1-terra` だけで、推論強度は `medium` 以上です。役割ファイルでモデルと既定の推論強度を固定し、自動の代替は行いません。メインチャットはユーザーがクライアントで選択した設定を使用し、このパッケージが稼働中のモデルを変更することはありません。候補パッケージは割り当て用に準備する引数に、役割で固定した設定をそのまま保持します。廃止済みの `astra_coordinator` は使えません。

監視の役割では、厳密に `gpt-6.1-terra`／`medium` を使います。どの役割にも代替モデルはありません。有効化時に実際に観測したモデルと推論強度の利用可否を記録してください。正確な役割設定を利用できなければ、準備済みの割り当ては拒否されます。

<a name="recovery-and-stop"></a>

## 復旧と停止

<a name="initial-activation-retry-v11"></a>

### 初回有効化の再試行（v1.1）

候補パッケージは初回有効化の前に `activation-attempt.json` を書き、監視が正常に起動しコアの状態が確定した後でのみ、確定済みと記録します。失敗の応答には `startup_retry.attempt_sha256` が含まれることがあります。この失敗記録は書き換え可能な実行ディレクトリの外で保存します。新しい実測の使用量入力、同じゴールの新しい観測、元の権限、`--startup-attempt-sha256 PRESERVED_FAILURE_PIN` を使って、最初と同じ `activate` または `bind-active-goal` を再試行します。編集後のジャーナルのハッシュを再計算して承認済み扱いにしてはいけません。

| 状況 | 使用できる操作 |
|---|---|
| 初回起動時の計測期限切れを記録済みで、識別情報と状態が変わらず、ワーカーが存在しないことを確認済み | 外部に保存した失敗の固定情報と、失敗後の新しいゴール観測・使用量記録を渡し、最初と同じコマンドを実行する |
| 既存のワークフローが停止確定済みで、計測期限切れを記録済み | 既存の検証付き `resume` に `usage_recovery: true` を渡す。停止確定後の確認事項をすべて適用する |
| 使用枠、早期予備枠、ユーザーの明示停止、その他の失敗、変更済みまたは未完了のジャーナル、識別できないワーカー | 技術的な迂回経路はない。証跡を保存し、該当する再開・照合の規則を満たす |

起動、状態確定、ロールバック、停止、権限遷移には候補パッケージが所有する同じロックを使います。理由の分からない `lifecycle.lock` を削除せず、実際の所有者と未完了の操作を調べてください。ネイティブの Codex ツールと一体のアトミックな処理ではありません。調整バッチは引き続き順次実行され、ジャーナルを持ちますが、アトミックではありません。

準備はネイティブで計測する前に済ませます。可能なら `sample_at + interval - min(15, interval / 4)` までに更新してください。早めに動くための目安であり、観測記録の有効期限は延びません。新しいサンプルの時刻、実プロセスとエポックの一致、ハートビート、サンプルの鮮度、リースをそれぞれ確認します。入力を反映するだけではリースは更新されません。週次枠の例外にはユーザーの実際の発言と明確な有効期限を使います。コアと監視処理は同じ枠を選び、両枠の生の計測値を保持します。

<a name="initial-native-goal-binding-n02"></a>

### ネイティブゴールの初回ひも付け（N02）

ネイティブゴールがすでにアクティブで、初期化にユーザーの発言の有効時間より長くかかった場合は `bind-active-goal` を使います。開始できるのは、何も行っていない非アクティブの schema2 の補助プログラムだけです。タスク、過去の操作フィールド、停止や完了の履歴、移行や再送防止用の予約がないことが条件です。既存の実行には現在の権限と新しいアプリ側の観測を使います。ネイティブゴールにひも付いた停止確定済みの実行は、停止後に `paused`／`blocked` を観測し、その後に同じゴールの新しい `active` を観測して再開できる場合があります。`updated_at` の変化だけで、ユーザーが状態を変えたとは判断できません。権限を保持したままアクティブなゴールが計測期限切れで中断した場合は、以下の技術的な復旧手順を使います。

`native_binding` には `binding_id`、ゴール・スレッド・実行の ID、新しい範囲 ID を持つ objective の範囲、ネイティブの `objective` の原文、元の `goal_created_at`、現在の `observed_at` を入れます。コマンドの `objective` には目的の原文をそのまま指定し、モデル、容量、実行一覧の通常の証跡も渡します。別個の `app_goal_observation` には同じゴール、スレッド、目的、作成時刻、観測時刻に加え、`status: active`、`source_kind: get_goal`、実際の観測記録の ID を入れます。観測は 60 秒以内で、未来の時刻は使えません。作成時刻は元の値を保持し、古くても構いません。説明用の前置きを足さず、ゴールの目的文をそのまま使ってください。

`interpretation` と `procedural_check` は、メインが個別に作成する空でない証跡です。ひも付け前に、現時点で許可されたゴールの文脈と、その後にユーザーから示された制限を確認します。過去の停止、報告、方針のメッセージからひも付けを導かず、`exact_quote`、`source_message`、`original_turn_id`、ユーザー発言の作成時刻を作り上げてはいけません。稼働中または状態不明の子エージェントが残っていてはいけません。補助プログラムは渡された情報の構造と整合性を確認し、実際のネイティブの出所はメインが取得します。

別個のネイティブ記録と再送防止の履歴は、後から人が再開・有効化しても保持されます。現在の根拠がネイティブの場合、`app-goal` で更新するたびにゴールとスレッドの識別情報、元の作成時刻、目的の原文を含めます。新しい使用量、実行一覧、容量、結果不明時の確認、割り当ての検証は引き続き必要です。ネイティブゴールがアクティブでも、補助プログラムの停止や停止確定は有効です。停止、スナップショット、停止確定、検証済みの復旧は通常どおりです。計測以外の理由で停止した後の `resume` には、停止確定後の既存の直接の `explicit_goal_continuation`、または `native_ui_resume: true` が必要です。後者では停止確定後に `app-goal` で `paused`／`blocked` を観測し、その後に同じゴールの新しい `active` の `get_goal` 記録を取得します。Unix 時刻の `updated_at` は停止と停止確定の両方より厳密に後でなければならず、同じ秒で前後が不明なら拒否します。両方の経路でチェックポイント、使用量、実行一覧を検証します。ネイティブの記録から操作した人は分からず、その記録は一度しか使えません。

<a name="expired-telemetry-recovery-under-existing-authority"></a>

### 元の権限が有効な場合の計測期限切れからの復旧

`usage_receipt_expired` は、メインエージェントが状況に応じた計測記録の期限を過ぎたことを示します。使用枠を使い切った証明ではありません。本格作業を止め、保存し、停止を確定します。固定済みの候補パッケージは `halt` の際に、同じ実行とエポックで監視プロセスが実際に記録した失敗を取り込みます。候補パッケージに `usage_failure` を独自に渡してはいけません。復旧専用の調整バッチは停止とスナップショットを扱えます。ライフサイクルの `halt` と `resume` は候補パッケージの直接のコマンドを使います。

この理由が記録された場合は、停止確定後に実際のネイティブ使用量と、同じアクティブなゴールについての新しい `get_goal` の観測を取得します。所有する子エージェントの一覧を更新し、チェックポイントと現在のファイルのハッシュ、およびワーカーの終了を確認します。`workflow usage` と `inventory` を記録した後、`workflow resume --input RECOVERY.json --usage-input USAGE.json` を実行します。`RECOVERY.json` に含めるのは `usage_recovery: true` と `app_goal_observation` だけです。ネイティブにひも付いた観測では、元の目的とゴール作成時刻を保持します。この経路は既存の権限を使うので、`updated_at` の変化、非アクティブな状態の観測、作り上げたユーザー発言や合成のクリック記録は不要です。候補パッケージは保存された失敗が実際の監視側の停止記録と一致するか確認してから新しいエポックを始め、監視が正常になるまで待ちます。期限のある週次枠の例外と過去の SAVE 記録を保持します。古いタスクは拒否され、暗黙には再開しません。

実際の使用枠や早期予備枠による停止、欠落・不正・別種の計測障害、原因の記録がない場合、ゴールの不一致、古い使用量、非アクティブなネイティブゴール、稼働中または不明な子エージェント、変更されたチェックポイント、受け入れ済みの再開で解除されていない明示的なユーザー停止は、この経路で拒否します。ネイティブゴールの状態を変更してはいけません。ユーザーは Continue で一時停止中またはブロック中のゴールをアクティブにできます。その場合は、実際にアクティブになったことを観測し、同じ技術的な条件を適用します。同じゴールがアクティブなら通常の自動ゴールターンでもこの技術的な中断を復旧できます。期限切れだけを理由に、再開の入力をもう一度求めたり `blocked` にしたりせず、ネイティブの `update_goal` の仕様に従ってください。アクティブ状態の時刻を、誰がクリックしたかの証明として扱いません。記録済みの明示的なユーザー停止を解除できるのは、正常に受け入れられた直接の再開か、現在ネイティブにひも付く実行に対する既存の検証済み UI 再開経路（非アクティブからアクティブへの遷移）だけです。`usage_recovery` 自体はその解除イベントを作りません。

ネイティブゴールとひも付かず手動監視だけで動く実行には、ワークフローの `usage_recovery` は使いません。明示的な再開と新しいエポックの仕様に従います。以前のパッケージで停止し、原因が記録されていない実行は、暗黙にアップグレードしたり原因を書き換えたりしません。固定した証跡を保持し、パッケージ更新とひも付けの仕様に従います。この復旧経路の対象は、当該パッケージが記録した原因です。出所が不足していればその旨を報告し、作り上げないでください。

<a name="authorization-lifecycle-a26--auth01"></a>

### 権限のライフサイクル（A26／AUTH01）

`authorization` は明示的なイベントオブジェクトです。空でない過去の `authorization` であっても、単なる文字列は拒否します。旧状態の取り込みは未対応です。新しい作業は、現行パッケージで現在の権限を使い、新しい実行として開始します。`interpretation` は別の最上位の文字列です。句読点も含めてユーザーの発言を正確に保存し、メインの解釈を連結しないでください。独立した `source_message` には、イベントと完全に一致する引用と出所情報を入れます。

再開時のペイロード例です。ID と時刻は合成データなので、実際の観測に差し替えてください。

```json
{
  "authorization": {
    "event_id": "user-event-42",
    "kind": "explicit_goal_continuation",
    "exact_quote": "Continue this goal now.",
    "source_kind": "user_goal_continuation",
    "source_id": "user-message-42",
    "goal_id": "goal-7",
    "thread_id": "thread-3",
    "run_id": "run-5",
    "scope": {"kind": "objective", "id": "scope-5", "objective": "Deliver the authorized project change"},
    "observed_at": 1791230401,
    "source_created_at": 1791230401, "original_turn_id": "turn-42", "observed_turn_id": "turn-42"
  },
  "interpretation": "Main classified this source as immediate continuation of the matching objective.",
  "source_message": {
    "source_kind": "user_goal_continuation",
    "source_id": "user-message-42",
    "exact_quote": "Continue this goal now.",
    "source_created_at": 1791230401, "original_turn_id": "turn-42"
  },
  "app_goal_observation": {
    "goal_id": "goal-7", "thread_id": "thread-3", "status": "active",
    "source_kind": "get_goal", "source_id": "actual-goal-tool-receipt",
    "observed_at": 1791230402
  }
}
```

出所の種別は `user_message` または `user_goal_continuation` です。ID と引用は空でない文字列です。イベントの観測は 300 秒で期限切れになり、未来の時刻は使えません。完了済みの実行をまたいでも、イベント ID と出所のメッセージは二度使えません。メッセージの識別情報は両方の種別を通じて、スレッド ID と出所 ID の組です。イベント ID や出所の種別を変えても、同じユーザーメッセージは再利用できません。アプリゴールの観測にはゴールとスレッドの一致、`get_goal` という出所、空でない観測記録 ID、イベント以降で 60 秒以内の有限な時刻が必要です。本格的な操作前に新しい実測のアプリゴールを取得し、`app-goal` で記録します。`task` と `prepare` は、現在の時刻と権限の識別情報に照らして保存済み観測を再検証します。60 秒ちょうどは許可されます。61 秒、未来の時刻、識別情報の不一致は、状態のバイト列を変えずに拒否します。使用量や実行一覧の更新ではアプリゴールの証跡は更新されません。これらはすべて**呼び出し元が渡す証跡**です。Python が確認するのは構造、一致、鮮度、状態遷移の条件です。プロバイダーへの問い合わせ、会話ログの認証、自然言語の分類、ツール記録の真正性の確認、実際のユーザー発言であることの証明は行いません。メインが本物の出所とツールの記録を取得・保存し、イベント種別を正しく分類します。作り上げた引用が二つ一致すれば、照合だけは通ります。独立した出所確認にはなりません。

| イベント種別 | 新規の有効化 | 停止確定済み・停止済みの旧目的 | 割り当てへの影響 |
|---|---|---|---|
| `explicit_task_authorization` | 別の実行・範囲、目的の一致、アプリゴールのアクティブ観測 | 再開不可 | 新しく許可された実行に限る |
| `explicit_goal_continuation` | アプリゴールのアクティブ証跡があれば、別の実行・範囲を許可 | 以下のすべての条件を通った場合のみ再開 | 正常に再開した後の新規タスク |
| `future_goal_intent` | 拒否 | 再開を拒否 | 旧作業の権限にならない |
| `policy_change` | 拒否 | 再開を拒否 | 旧作業の権限にならない |
| `independent_report_request` | `kind: report` の別範囲で、報告の正確な目的に限る | 再開と停止確定済みの実行への上書き有効化を拒否 | 別個の報告実行のみ。旧作業は停止確定のまま |
| `explicit_stop` | 拒否 | 識別情報と範囲を一致させて `observe-authorization` で保存 | 新規 task／prepare を即座に止める |

`observe-authorization` は将来の意図、方針の変更、別の報告依頼、範囲を限定した停止イベントを記録します。目的を有効化・再開したり、現在の権限を書き換えたりはしません。停止確定済みの目的に関する報告は、別の補助プロジェクトと状態で実行します。停止した実行を上書きしてそのタスクにアクセスすることはできません。`app-goal` は新しい観測を別に記録します。paused、blocked、stopped、complete の観測は、稼働中の補助プログラムを停止させます。その後の active 観測だけではユーザーによる再開を証明できません。ネイティブ UI からの再開には、停止確定後にまず非アクティブ状態を観測する必要があります。計測期限切れが停止理由として記録されている場合は、既存の権限の下で `usage_recovery` を使います。`status` は補助プログラムの `status` と `app_goal_observation` を別々に返します。割り当てのプロンプトには、許可範囲、ゴール・スレッド・実行の識別情報を含めます。

ユーザーの直接のメッセージで再開するには、停止と停止確定より厳密に後に観測された新しい `explicit_goal_continuation` を渡します。保存済みのすべての識別情報と正確な範囲が一致する必要があります。まず停止確定後の実際の使用量と子エージェントの実行一覧を読みます。使用量は新しく、残り利用枠がしきい値を上回り、状況に応じた期限内であることが条件です。新しい実行一覧には、稼働中または状態不明の所有する子エージェントがいてはいけません。チェックポイントの復元と現在のファイルハッシュを再検証します。停止確定後、かつ再開指示以降に、対応するアプリゴールがアクティブであることを観測します。検証が不完全な停止から復旧するには、チェックポイントの修復が必要です。再開に成功すると古い未完了タスクを拒否し、新規割り当てを可能にします。子エージェントを暗黙に再開することはありません。権限情報がない、古い、再利用、不正な形式、または再開用でない場合は、状態のバイト列を変えずにコマンドを拒否します。

ユーザーが明示的に停止を指示した場合、メインは本格作業と新規割り当てを直ちに止めます。復旧に必要な短い処理に限り、所有する書き込み担当の停止と応答確認、作業の保存、停止の確定を行います。停止中に新しい計画、詳細な引き継ぎ、復旧基盤を作らないでください。アプリ側の観測は補助プログラムの状態遷移とは別に記録します。補助プログラムはネイティブツールを横取りしません。どの出所に当たるかを判断し、ネイティブ側の停止手順を守るのはメインの責任です。A26 では、使い捨ての Python テストに加え、実際のネイティブの再開・停止の記録と、無許可のネイティブ操作がなかったかの独立監査が必要です。

`stop` は割り当てを止め、稼働中の書き込み担当への SAVE_ACK 要求を返します。各担当から短い応答を一つずつ受け取ります。最大 30 秒待っても応答しなければ、必要に応じて所有する担当を中断し、メモリ上に未保存の内容が残っている可能性を伝えます。スナップショット前に、ディスクへの書き込みが止まったことを確認してください。補助プログラム自身はメッセージ送信、プロセス停止、継続的なポーリングを行いません。

監視が異常な場合や `SAVE_AND_STOP` を記録した場合も、固定済み候補を通して `stop` を実行できます。復旧の前提として正常な計測を要求しません。直接の `stop` → `snapshot` → `halt` と復旧専用の調整バッチは、同じ許可コマンド一覧を使います。これによって、新規タスク、SAVE ラッチの解除、異常なリースの更新、作業の再開が許可されることはありません。`halt` では引き続き、実行一覧に動作中の担当がいないこと、チェックポイントの完全性、所有ワーカーの終了を確認します。

書き込みが停止したことを観測してから、`snapshot` に `files`（変更、作成、削除したすべてのプロジェクト相対パス）、`next_action`、`writers_quiescent: true` を渡します。すべてのタスクが宣言したファイルは自動的に含まれます。メインの調整役が書いたファイルと未追跡ファイルは明示的に含めます。コピー中にファイルハッシュが変わってはいけません。マニフェストは存在しないパス・削除済みのパスと状態のコピーを記録します。内部の新しいディレクトリで復元を試し、ハッシュを検証します。認証情報はアップロードしません。外部にある復旧対象の成果物は、所有するツールで先にローカルへ保存しておく必要があります。

ホストのツールを使い、所有するエージェントを中断し、所有するプロセスだけを停止します。`halt` には新しい `inventory`、`observed_at`、`owned_processes_stopped: true`、実ツールで観測した `stop_evidence` を渡します。チェックポイントと現在のファイルハッシュは再検証されます。スナップショットや復元に成功できない場合、`degraded: true`、`reason`、`next_action`、実際の停止証跡を使い、復旧を検証済みと報告してはいけません。`resume` には、期限切れ計測の復旧、直接の再開、より新しいネイティブ UI の遷移のいずれかの経路と、上記の復旧確認がすべて必要です。検証が不完全な停止から再開する場合は、先にチェックポイントを直します。利用枠のリセットを再開許可として自動的に使ったり、ネイティブゴールの状態を自動変更したりしてはいけません。計測の復旧は、すでに許可されているアクティブなゴールでの動作を回復するだけです。

`restore` は検証済みチェックポイントをプロジェクト外の新しい保存先へコピーします。プロジェクトの内容は `files/` の下に、復旧のメタデータはその外に置きます。マニフェストは存在してはいけないパスを記録します。使用中のプロジェクトファイルを削除・上書きすることはありません。スナップショットが永続的に確定したら、現在と一つ前の正常なチェックポイントを保持します。整理するのは所有している古いディレクトリだけで、リンクを拒否し、出所不明の内容を残します。`compact` には稼働中の子エージェントと未完了タスクがなく、検証済みスナップショットがあることが必要です。完了したタスクの記録を除去します。`complete` は成果物を引き渡した実行を閉じます。その後の仕事には新規の有効化が必要です。

## 機械的な調整と永続的な割り当て記録（N05）

`scripts/candidate.py <global pins/options> coordination --input <request.json>` は、標準ライブラリで動き、モデルを使わないアダプターです。リクエストの形は `{ "batch_id": "unique_id", "steps": [{ "key": "unique_step", "command": "task", "payload": { ... } }], "seen": [] }` です。最大 64 ステップを順番に実行します。各ワークフローコマンドには固有の検証、状態ロック、確定処理があり、バッチ全体は意図的にアトミックにしていません。単独の読み取りには `read` を使い、`payload.paths` に正確なプロジェクト相対パスを渡します。ジャーナルには読み取ったテキスト、バイト数、SHA-256 を保存し、存在しないファイルの固定値は null にします。阻害要因、観測したセッションの識別情報、ワークフローソースの固定値、ジャーナルのパス、ステップごとの結果、結果トークンを含む簡潔な判定を一つ返します。生のリクエスト、ツール記録、結果は `.agent-workflow-v1-1/runs/<run-id>/coordination/<batch_id>.json` に保存されます。受け取り済みの結果トークンを `seen` に渡すと、変化のない完了結果の再表示を抑制できます。ネイティブツールの出力はこのアダプターの対象外です。

各ステップは実行前に、変更前の状態ハッシュとともに `pending` としてジャーナルに記録します。その後、変更後の状態ハッシュと結果を `applied`、またはエラーと変更後の状態ハッシュを `failed` として別に保存します。状態を変更した後、結果を記録する前にプロセスが落ちると、`pending` のまま残ります。そのバッチを再起動すると、新しいステップは適用せず、阻害要因を返します。適用済みステップは二度と実行せず、失敗したステップでバッチを止め、それまでのすべての結果を保持します。同じ ID を異なるリクエストに用いたり、実行の意図や結果の証跡を消したりしないでください。状態のバイト列が同じでも、スナップショットや復元のファイル操作はすでに発生しているかもしれず、再試行が安全とは判断できません。永続ジャーナルと現在のコア状態を調べ、実際の外部ツール記録を保持し、不明な副作用を明示的に解消した後、新しい限定的な照合用バッチを使います。クラッシュを自動で成功に繰り上げる処理はありません。ジャーナルとコアのロックはそれぞれの確定処理を保護します。書き込みはメインだけが担当し、他のツールまで含めたトランザクションは提供されません。古いロックは、削除前に所有者を調べます。

ジャーナルを使うネイティブの割り当ては、次の手順で行います。

1. 割り当て直前の判定で実際のネイティブ実行一覧を取得し、`inventory` に記録します。`prepare` は通常どおりの正確なネイティブ引数と `intent_id` を返します。この ID はコアのタスクに永続的に予約されます。
2. 実際のネイティブツールを呼ぶ直前に、`id` と `intent_id` を指定して `dispatch-start` を実行します。権限、アプリ側観測の鮮度、使用量と SAVE、実行一覧、タスクと入力の有効性、書き込み先の割り当て時ハッシュを再検証します。正確な `collaboration.spawn_agent` の引数を返す前に `uncertain` を記録します。タイムアウト、結果の消失、再起動が起きても、これで二重割り当てを防ぎます。ネイティブ呼び出し前のクラッシュも、結果が不明な点は同じです。解消前に実際の一覧を調べます。従来の直列の `prepare` → ネイティブ呼び出し → `record` も利用できますが、呼び出し前に結果不明を記録する仕組みはありません。
3. メインは対応するツールを通じて実際の `collaboration.spawn_agent` を直接呼び出します。Python や `functions.exec` を介さず、実際の結果を保存します。新しい実行一覧は `observation: { "source_kind": "collaboration.list_agents", "source_id": "caller-capture-correlation-id", "evidence_path": "operations/raw-native-inventory.json", "sha256": "<actual-file-hash>" }` で記録します。そのプロジェクト相対ファイルに生の出力をそのまま一度だけ保存し、状態とジャーナルには参照先と固定値だけを入れます。パスとハッシュの代わりに `receipt: <actual-native-output>` をインライン指定することもできます。その場合は生の出力が状態とジャーナルに重複します。どちらか一方だけを指定できます。ネイティブの出所情報は `dispatch-start` と、遅れて成功が分かった場合の照合に必須です。60 秒の有効期限や ID・状態の確認の代わりにはなりません。コアは使用するたびに証跡を読み直し、固定値を確認します。`native_inventory(raw)` は実際の対応出力 `{agents:[{agent_name,agent_status}]}` を正規化します。文字列 `running` と `idle` はそのまま、`interrupted` は `stopped`、厳密に `{completed: <final text string>}` の形のオブジェクトは `done` になります。不明、形式不正、曖昧、重複の項目は拒否します。呼び出し元で正規化した一覧は順序によらず生の出力からの投影と一致する必要があります。完了時の全文は証跡側に保持します。
4. 結果が不明なタスクを照合するには、`id`、`evidence`、`no_owned_work_running: false`、正確な `submitted_arguments`、実際の `session_id` と `receipt` を渡します。観測できた実効モデルと推論強度は任意です。記録はオブジェクトであり、`id`、`agent_id`、`session_id`、`task_name` のいずれかが、一覧のセッション識別情報と一致しなければなりません。そのセッションは、保存した意図の時刻以降の新しい実行一覧に、既知の状態で存在する必要があります。準備した引数と変更不可の入力は引き続き完全に一致させます。セッションの再利用は拒否します。`Coordination.receipt(...)` は遷移を試す前に実際の生の記録をジャーナルへ書きます。CLI からも同じ `reconcile` ステップを送れます。証跡がない、古い、出所が違う、形式が崩れている、識別情報に矛盾がある場合、タスクを running に移せません。停止途中に遅れて現れたセッションは、補助プログラムの状態を `stopping` として、復旧用に記録します。権限の再開や新規割り当てにはつながりません。入力の無効化で照合できない場合、ツール記録とジャーナルは保持し、実際の子エージェントをネイティブツールで止めます。
5. 実際の新しい一覧で終端状態を確かめ、重大な成果の受け入れ時に独立レビューと出力の固定値を確認してから完了を記録します。終了や復旧では既存の確認条件に従って実際の一覧を取り直します。その一覧で所有する稼働中の作業も状態不明の作業もないと確かめた場合、既存の `reconcile` に `no_owned_work_running: true` を指定すると、結果が不明なタスクを拒否します。再試行はせず、実行記録なしに成功を推定することもありません。

補助プログラムは渡された構造、出所ラベル、鮮度、整合性を検証します。呼び出し元、ネイティブツールの記録、会話ログの真正性は確認できません。内部で整合するネイティブラベルを付けた捏造オブジェクトを、ローカルでは見分けられません。メインが実際のネイティブ出力を取得し、保存する必要があります。プロバイダーが記録 ID や呼び出し ID を公開しない場合、`observation.source_id` はメインが生成した、保存済みの一つの生の出力にひも付けるための ID です。呼び出し側が用意したものだと明示し、プロバイダー発行または認証済みと主張しません。実際の起動結果が持つエージェント、セッション、またはタスクの識別情報は引き続き一致する必要があります。記録の識別情報を照合しても、メタデータの真正性は証明されません。ネイティブの準備、起動、記録はアトミックではなく、アダプターはネイティブツールを横取りせず、その出力も抑制しません。ジャーナルの `source_pin` は、workflow.py と coordination.py の両方の SHA-256 を含む正規形のマップをハッシュ化した値です。

`collaboration.list_agents` は、既知の正規タスク接頭辞を指定する `path_prefix` に対応しています。必要な所有グループごとに、確認時点の観測を一度行います。ルートが不明なら、先に一覧を調べます。接頭辞で検索したときも、一致する完了済みエージェントの最終回答全文が返る場合があります。ネイティブの `compact`、`exclude_completed`、出力を絞り込むスイッチを作り上げてはいけません。ローカルジャーナルの結果トークンが抑制するのは、すでに渡した補助プログラムの結果だけです。プロバイダーからのバイト列をフィルタリングした証拠にはなりません。

正式に対応するソース版とステージ済み版のサブプロセスの入口、条件付きバッチ、ライフサイクルを実際に検証するには、リポジトリのルートで `python -X utf8 -B -m unittest discover -s skills/agent-workflow-v1-1/tests -p test_candidate_coexistence.py -v` を実行します。過去のコア直接実行のフィクスチャ記録は、候補パッケージの稼働準備ができたことを示しません。双方の経路で、同じタスク・入力の固定、準備、合成ツール記録の登録、合成した終端観測、受け入れ、スナップショット検証、終了を行います。このテストはサブプロセスのコマンド数、終了コード、実際の標準出力・標準エラー出力のバイト数を報告します。これはモデル化したメインの判断の区切りで、メインのモデルを実際に何度呼び出したかの計測ではありません。合成した記録やコールバックは、ネイティブの割り当てを証明しません。メインは、実ツールの記録を用い、実際の直列・バッチのネイティブ経路を別途計測する必要があります。タイミング、一時的な絶対パスの長さ、シリアライズ方法により計測したバイト数は変わり得ます。

<a name="install-and-update"></a>

## インストールと更新

`tooling/build-candidate.py` で、同じ入力から同じ結果になる候補パッケージの内容、ZIP、外部ビルド記録を作成します。正式な候補の `install --destination <explicit-directory>/agent-workflow-v1-1` は同梱内容を全バイト検証します。所有するインストールの内容が同一なら何も書き換えません。`--update` は改変されていない所有インストールを置き換えます。編集済みまたは所有外の内容は拒否します。配置の確定に失敗したときは、トランザクションとして以前のディレクトリを復元します。更新に成功すると、前のパッケージやロールバック用のアーカイブは保持しません。正確なコマンドと信頼の基点の扱いは [ランタイムのひも付け](coexistence.md) を参照してください。

スキルの暗黙の選択は無効です。実行ごとに固定したソース版、ステージ済み版、またはインストール版の候補パッケージへの対応が、実行の識別情報です。実行の途中で切り替えないでください。監視エンジン、役割、指示は `private/limit-watcher` の下で保守・同梱されます。これを制御するのは、固定済み候補パッケージのエントリーだけです。候補パッケージを更新するときは、新たに承認された実行を使います。既存の証跡の移行やひも付け直しは行いません。パッケージをビルドまたはインストールしただけでは AGWF は有効にならず、エージェントも登録されません。プロジェクト準備のためにユーザーが AGWF を明示的に呼び出した場合は、その範囲で上記の起動手順が必要です。メインクライアントのモデルを選択するのは引き続きユーザーです。
