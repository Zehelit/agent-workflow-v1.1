# ネイティブ使用量の受領記録

明示的に許可され、有効な AGWF 実行だけに使います。現在の明示呼び出しには対象範囲での起動が必要です。ネイティブ目標を作れない場合は[運用](operations.md)の手動監視を使います。パッケージの更新、スキルの検討、使用量の記録だけでは無効なワークフローは再開しません。

メインエージェントが既存の Codex 接続で `mcp__codex_app__get_usage_limits` を呼びます。Python は別の app-server や CLI を起動せず、認証ファイル、私有通信経路、モデルリクエストを使いません。バックグラウンドは受領記録の鮮度を確認します。作業の境界でホストツールを呼ぶのはメインです。

実際のツールの応答から非公開の入力 JSON を作ります。

```json
{
  "source": "mcp__codex_app__get_usage_limits",
  "sourceId": "actual-tool-call-receipt-id",
  "observedAt": 1800000000,
  "result": {
    "rateLimits": {
      "limitId": "codex",
      "primary": {"usedPercent": 25, "windowDurationMins": 300, "resetsAt": 1800010000},
      "secondary": {"usedPercent": 30, "windowDurationMins": 10080, "resetsAt": 1800600000}
    }
  }
}
```

数値は例です。実観測の時刻、記録 ID、値は保持します。捏造したりファイルを書いた時刻に置き換えたりしません。複数グループが返る場合は `rateLimitsByLimitId.codex` を優先します。複数グループに Codex がなければ拒否します。両ウィンドウの長さとリセット時刻が必要です。必要な使用量フィールドだけをコピーし、アカウント、プロフィール、クレジットは不要です。`watcher/usage-source.json` には許可済みウィンドウ項目、出典と観測の識別情報、紐付く実行とエポックだけを保存します。

`workflow activate --input AUTH.json --usage-input USAGE.json` と `bind-active-goal` は起動前に権限を検証します。`resume` にも `--usage-input` で新しい記録が必要です。以前のエポックの記録は再利用できません。手動の `watcher start --usage-input USAGE.json` も同じ検証を行います。記録がない場合や既に期限切れの場合は、プロセスを起動しません。

作業中は `watcher ingest --usage-input USAGE.json` またはワークフローや調整の `--usage-input` で新しい観測を登録します。`ingest` はデータ登録だけです。ワークフローの有効化、監視の起動、権限の更新、SAVE の解除は行いません。新しいファイルは以前の期限を待たずに評価を促します。監視が処理するまで状態に前回の評価が残ることがあるため、重要な割り当ては新しい健康状態を確認してから行います。

メインは動的期限までに再測定します。上限は 300 秒で、しきい値に近い場合や消費が速い場合は短縮されます。古いファイルの再読み込みは新しい観測を作りません。新データがない場合は検証を一度再試行し、それでもなければ SAVE_AND_STOP を記録します。`usage_receipt_expired` が記録され、同じ許可済み目標がまだ有効なら `workflow resume` と `usage_recovery: true` で[技術復旧](operations.md#expired-telemetry-recovery-under-existing-authority)できます。新しいデータだけでは SAVE は解除されませんが、この復旧は別のユーザーメッセージを必要としません。利用枠が尽きた場合や明示停止の場合は、各条件を適用します。次の呼び出しに間に合うように更新します。期限まで待つという意味ではありません。中断できない処理が長いと更新できないことがあり、バックグラウンドがホストツールを自動取得する仕組みではありません。

形式不正、実行やエポックの違い、未来または期限切れ、時刻逆行、内容を変えた再送は拒否します。同一の記録を再登録しても何も変わりません。時刻と出典は呼び出し側が提示する証拠で、JSON 形式はプロバイダーを認証しません。原本を非公開で保管し、出典ラベルだけで証拠としないでください。

測定エラーでは許可済み `diagnosticCode` とエラー種別をサンプルや状態で返します。`watcher/diagnostics.json` は構造化された 20 件までを保管します。例外原文、認証情報、ツール応答全体は含みません。予期しない Python プロセスの失敗はローカルの `worker-stderr.log` に残します。別サーバーを起動しないため、それに由来する stderr はありません。

candidate コマンドと監視評価ではパッケージ全体を検証します。新規入力の評価も含みます。ハートビートは実行・エポックの制御と健康状態だけを検証し、全ファイルを再ハッシュしません。依存関係の変更は次の測定またはコマンドで拒否されます。全ハートビートでの検出を保証するわけではありません。

単体試験は実ファイルへの保存と読込、厳密な JSON、失効・再送・識別、しきい値、診断範囲、測定時にプロセスを作らないことを確認します。実環境の Remote の受け入れは別に行います。ユーザーが明示して再度有効にするまではインストールを無効のまま保ち、保守だけで本番監視を起動しないでください。
