# 状態の互換性と復旧の範囲

v1.1 の実行環境が受け入れるのは、承認済みで変更できない実行領域にある現行 schema2 の状態です。不明、破損、旧形式の状態は運用状態を書き換えずに拒否します。以前の許可文、保存済みタスクの受領記録、期限切れの目標観測は新しい権限を与えません。

固定された入口 `scripts/candidate.py` に移行コマンドはありません。コアにも旧状態の変換器や旧認可の検証器はありません。別のインストールからの自動取り込み、初期化、パッケージのロールバックは非対応です。承認済みの更新後は新しい実行を始めます。既存の実行のマニフェストやヘルパーの対応を変えないでください。

復旧には受け入れた実行の検証済みチェックポイントと、次の操作に有効なユーザーの許可を用います。元の時刻、再利用防止の予約、ファイルの整合性、書き込み停止の観測を維持します。以前の停止や続行メッセージは履歴として残ります。ヘルパーが復旧対象の目標を自動的に有効化することはありません。

新しいチェックポイントの所有者は `agent-workflow-v1-1` です。コア単独の既定ディレクトリは `.agent-workflow-v1-1`、サポート対象の固定入口は `.agent-workflow-v1-1/runs/<run-id>` を使います。以前の `.agent-workflow` と `.agent-workflow-v1-0` は取り込みません。予約済みのため、タスクパスや復元先にはできません。現在のスナップショット整理で旧所有マーカーは削除されません。コア CLI の直接呼び出しは拒否されます。

## インストールを技術識別子 1.1 に移す

1. 既存のプロセスと書き込み担当を調べ、所有する作業だけを停止します。以前のインストールを移す前にそのプロセスの実際の終了を確認します。
2. 旧パッケージを所有記録と照合します。スキル検出対象外にバックアップしてハッシュを確認します。編集があれば先に保存します。
3. 新しいマニフェストと外部固定値で `skills/agent-workflow-v1-1` へ新規インストールします。旧識別子に `--update` を使用しません。
4. 検出パスを変える前に、新しい入口と固有の検証実行 ID で `workflow validate` を実行します。返された識別子、版、作業範囲、マニフェスト固定値を照合します。`run-binding.json` は作成されますが、目標、ワークフロー状態、監視は起動しません。
5. 新しい呼び出し名は `$agent-workflow-v1-1` です。検証後にメインとロールのスキルパスを更新します。有効・無効と明示呼び出しの設定を保持し、並行編集を上書きしません。所有プロセスをもう一度調べ、別セッションが使用中のインストールは移しません。安全な移行後、旧パッケージをスキル検出の範囲外に保存し、設定とバックアップを確認します。
6. 古いチェックポイント、紐付け、受領記録の識別情報、パス、ハッシュを維持します。新パッケージには新しい実行を使います。未完了作業を引き継ぐ場合は、以前に検証した成果物と現在の実際の許可を別に提供します。
