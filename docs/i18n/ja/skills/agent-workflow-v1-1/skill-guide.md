# agent-workflow-v1.1

今回の実行でユーザーが agent-workflow-v1.1 を明示的に選択した場合に限り使用します。暗黙に呼び出すことはできません。今の明示的な呼び出しを受けたメインエージェントは、準備や小さな作業も含め、ユーザーが許可した範囲の AGWF を同じターンで起動します。過去に無効化されていても、今の選択でその範囲の実行を再び有効にできます。以前の選択や別セッションでの選択には、その効力はありません。このスキルを話題にする、引用する、調べる、保守するといった依頼は、中止済みのプロジェクト作業を再開する指示には当たりません。メインチャットが調整の主体として、成果の引き渡し、状態の書き込み、実際のエージェントへの割り当てを担います。モデルと推論強度はユーザーがクライアントで選択し、スキルはどちらも割り当てません。起動後も、小規模な作業はメインエージェントが担当します。チームの利用は任意ですが、起動と監視は必須です。

<a name="required-startup-on-explicit-invocation"></a>

## 明示的な呼び出し時の起動手順

本格的な調査、プロジェクトの変更、テスト、委任に先立ち、新しいネイティブ使用量の観測記録を取得し、固定済みの候補パッケージを通じて起動します。必要な証跡がそろっていれば、許可された `workflow activate`／`bind-active-goal` を使用します。ユーザーが準備に作業を限定している場合、ネイティブゴールの作成を禁止している場合、またはアクティブなゴールがない場合は、[運用ガイド](references/operations.md) の手動手順で統合監視プロセスを起動し、許可された範囲で作業します。明示的な許可なしにネイティブゴールを作成しません。スキルの読み込み、セレクターの有効化、一度きりの使用量確認だけでは起動手順は完了しません。

起動したことを実際に確認します。選択した実行 ID とエポックに対応する新しく正常なサンプルがあり、この実行が所有する監視プロセスが稼働していることを確認してください。ワークフロー全体を起動する場合は、ワークフロー状態がアクティブであることも確認します。本格的な作業前に起動結果を報告します。同じ許可範囲で正常な実行がすでにあれば再利用し、ワーカーを重複して作成しません。停止後の明示的な再呼び出しでは、既存の再開手順で新しいエポックを開始できる場合があります。その際は、ユーザーの操作を正確に記録し、すべての復旧確認を行います。

起動が拒否された、証跡が得られない、または利用枠の状態により `SAVE_AND_STOP` が必要になった場合は、具体的な理由を直ちに報告し、必要な復旧処理だけを行います。メインエージェントだけで依頼された作業を黙って続けてはいけません。起動後に停止の指示があればそちらが優先します。停止中にこのスキルを調べたり更新したりしても、以前の割り当ては再開されません。

ワークフローのコマンド、調整、統合された使用量監視には、固定済みのエントリーポイント `scripts/candidate.py` を使います。承認されたマニフェストの固定情報があれば、ターミナルから直接実行できます。この実行にスキルの呼び出しや監視処理の呼び出しは不要です。コア CLI の直接実行は未対応で、拒否されます。外部の信頼の基点と実行を分離する契約については [ランタイムのひも付け](references/coexistence.md) を参照してください。実行を開始する際は [運用ガイド](references/operations.md) も読みます。モデル設定の出所は役割ごとの TOML と `private/limit-watcher/role.json` です。監視エンジン、運用指示、役割はこのスキルの中で保守、同梱、検証されます。監視用の別スキルやランチャーはありません。

<a name="role-skills-and-memory"></a>

## 役割のスキルとメモリ

定義済みの各サブエージェントには、専用の `SKILL.md` と `MEMORY.md` があります。coordinator、architect、implementer、researcher、verifier は `roles/<role>/` にあり、limit_watcher は `private/limit-watcher/` にあります。それぞれの役割定義は対応する文書を明示的に参照します。ランタイムは割り当ての準備時、対象の役割に対応するスキルとメモリだけを含めます。必要な文書がなかったり、空だったりする場合は読み込みを拒否します。臨時の専門担当は、ベースとなる役割の文書に加え、タスク固有の専門分野の指示を受け取ります。

役割スキルにも、明示的な呼び出しに限定する個別の方針があります。役割スキルは内部の割り当てのための指示です。独立したエントリーポイントとして直接選択された場合、準備済みの役割の割り当てと、実際のモデル・推論強度が一致する証跡がそろわなければ、不足している証跡を示して停止します。役割スキルが AGWF を有効化したり監視を開始したりすることはありません。ワークフローを無効にするときは、スキルのエントリー七つすべてを無効化し、所有しているワーカーを停止します。更新しても自動的に有効にはなりません。

役割メモリは持続する参照資料です。権限を与えたり、現時点のプロジェクトの証跡に代わったりはしません。過去の観測を作り上げないでください。メモリに追加したい項目はメインエージェントに返し、メインエージェントがレビューしたうえで実行と実行の間に保守対象の文書へ反映します。役割文書はパッケージマニフェストに含まれるため、メモリを変更するときも通常のパッケージ更新と新しい実行へのひも付けが必要です。タスクの進行中にインストール済みスキルを編集してはいけません。

<a name="integrated-limit-watcher"></a>

## 統合された使用量監視

許可された `workflow activate` または `bind-active-goal` を固定済み候補経由で実行すると、モデルを利用しない監視プロセスが自動的に起動します。有効化前に、現在の Codex 接続から実際の `mcp__codex_app__get_usage_limits` の観測記録を取得し、`--usage-input` で渡します。[ネイティブ使用量の仕様](references/native-usage.md) に従ってください。監視処理は Codex app-server を起動せず、PATH から CLI を選択せず、別の通信経路に接続しません。候補パッケージはワークフローをアクティブとして記録する前に、新しく正常なサンプルを確認します。観測記録がなかったり期限切れだったりする場合、有効化を拒否します。`resume` にも同じ条件で取得した新しい観測記録と、新しいエポックが必要です。停止理由として `usage_receipt_expired` が記録された場合には、以下の計測復旧手順を使います。他の停止ではユーザーの直接の再開指示、または受け入れ条件を満たすネイティブゴールの状態遷移が必要です。

許可された作業中、メインの調整役は状況に応じた 300／120／60／30 秒の期限内にネイティブ観測記録を更新します。バックグラウンドの Python ワーカーは渡された値を検証し、新しいデータがなければ作業を止める側に倒れます。ホストのツールを自ら呼び出すことはできません。ファイルを読み直しても観測時刻は更新されません。有効な実行コマンドは 600 秒のリースを更新します。監視が正常でなければ新しい作業はブロックされ、復旧操作は利用できます。`complete` と `halt` は所有ワーカーを停止し、終了を確認します。ハートビートではパッケージのハッシュを計算せず、実行とエポックの所有関係を確認します。依存関係全体の確認は、コマンドと計測の境界で行います。作業の区切りでは `workflow status` を使います。チャットで何も起きないことはデータやリースを更新しません。スキルが明示的に選択されたときも、起動の実行と確認はメインエージェントの責任です。クライアントにプロセスを自動起動する機構はありません。手動の `watcher start/ingest/status/renew/stop` にも同じ観測記録と権限の条件が適用されます。

残り 25% では完了済みの作業を検証済みチェックポイントとしてまとめます。残り 20% または早期復旧を求めるシグナルが来た時点で、新しい作業を止め、書き込み中の担当から簡潔な応答を求め、必要なファイルを検証し、この実行が所有するワーカーだけを停止します。使用量が得られず不明な場合は一度だけ再試行し、それでも分からなければ保存して止めます。`SAVE_AND_STOP` を受けたメインの調整役は、エージェントを待たず即座に行動します。計測の期限切れは技術的な中断です。枠を使い切ったことやユーザーが許可を撤回したことの証明にはなりません。保存して停止した後、停止理由が `usage_receipt_expired` と記録されていれば、元の許可が有効でネイティブゴールがアクティブな場合に計測を復旧できます。その際は `resume` に `usage_recovery: true` を渡し、新しい実測の観測記録、同一ゴールの新しい観測と一覧、変更されていない検証済みチェックポイント、所有ワーカーが停止済みであることをそろえます。候補パッケージは `halt` 時に監視側の実際の理由を記録します。クォータ、早期予備枠など別の失敗、ユーザーによる明示的な停止、非アクティブのゴールは、この復旧経路では拒否されます。証跡がそろった場合はこの手順で復旧します。計測データが期限切れだったことや一時停止状態を観測していないことだけを理由に、ユーザーへ改めて再開の入力を求めないでください。計測の期限切れだけを理由にネイティブゴールを `blocked` にしません。その判断はネイティブゴールツールが定める条件に従います。この手順で復旧するのは監視と補助プロセスです。ネイティブゴールのステータスは変えず、ユーザーの発言や画面操作を作り上げることもありません。他の停止にはそれぞれの再開条件が適用されます。利用枠のリセットを自動的な再開の根拠としたり、ネイティブゴールの状態を自動変更したりしてはいけません。週次枠の例外にはユーザーの実際の言葉と明確な有効期限が必要です。例外時も両方の枠を計測します。復旧判断が曖昧な場合に限り、統合された `limit_watcher` 役を、厳密に `gpt-6.1-terra`／`medium` で使えます。利用できない場合はその不足を報告します。[運用ガイド](references/operations.md) と [監視担当の役割](private/limit-watcher/limit_watcher.md) を参照してください。

今の状態を必要な範囲だけ引き継ぐには、[コンテキストの選択と受け入れの仕様](references/context.md) に従います。元の権限のタイムスタンプ、固定した証跡への参照、レビュアーの反証を保持します。コンテキストを表示しただけでは割り当ての権限は生まれず、キャッシュのメリットも保証されません。ネイティブ実行の完了と、独立した成果物の受け入れは、それぞれ版を持つ別個の観測です。重大な結果の独立レビューに先立ち、モデルに依存しない生成側の確認を実行します。

子エージェントには目的、必要な入力、書き込めるパス、受け入れ基準を渡します。メインの会話を複製せず、新規コンテキストで開始します。実装セッションの名前は frontend、backend、editor、data_analysis など実際の仕事に合わせます。恒久的な専門役割を新設する前に、関連する既存のプロジェクトスキルを利用します。専門性の高い作業には、適切なベース役割を使い、具体的な名前、分野の指示、必要な情報源とツール、受け入れ基準を添えて臨時の担当を設けます。既存の専門役割やユーザーによる別個の呼び出しは不要です。

researcher は証拠を収集し、要点をまとめます。implementer は設計、実装、修正をします。verifier は重大な結果を独立して確認します。architect が扱うのは、判断に費用がかかる設計上の選択や技術的な意見の相違です。すべてのタスクに関与するわけではありません。機械的に繰り返す処理はスクリプトに任せます。まず適した既存のスクリプトを利用し、繰り返しや信頼性のために必要なら、プロジェクト内にスクリプトを作って検証し、再利用します。この判断はタスクに応じてエージェントが行います。バックグラウンドで待機する常駐スケジューラーや、恒常的な Admin・Executor の階層はありません。

同時に同じファイルを書き込む担当は一人にします。共通インターフェースを変更する前に専門担当同士で合意します。セキュリティ、認証、データ喪失のおそれ、共通 API、広範な挙動の変更は独立して検証します。範囲が狭く元に戻せる作業はメインの調整役が検証できます。生ログの代わりに、結論、変更したパス、その証跡を返してください。

現在のユーザー権限とプロジェクトの制約に従います。停止指示があれば明示的な再開まで追加の割り当てを取り消します。保持するのは現在進行中の作業と長期的に有効な判断です。自分が作った一時資料は復旧で使う可能性がなくなってから削除します。メッセージの一律な長さ制限や強制的な会議は設けません。

補助プログラムは自分を経由する操作を検証します。ネイティブツールの呼び出しを横取りしたりプロセスを自動停止したりはしません。メインの調整役が、返されたツール呼び出しを実行し、結果を記録し、実際に動いているものを一覧で確認します。メタデータなしに、要求したモデルを実測済みの実効モデルとして報告してはいけません。

<a name="coordination"></a>

## 作業の調整

依存関係のある複数の専門分野にまたがる大きな作業を割り当てる前に、`coordinator` サブエージェントに、タスクの分割、依存関係、専門担当の選定、ファイルの担当案、受け入れ基準を求めます。大幅な範囲変更、専門担当の結果に未解決の食い違いがある場合、新しい計画が必要なほど失敗が繰り返された場合にも相談します。小規模な作業、独立した作業、日常的な進捗の把握はメインの調整役が担当します。

目的、現時点の制約、分かったこと、関連するソースの位置を、新規コンテキストで渡します。coordinator が返すのは読み取り専用の計画です。エージェントの作成やワークフロー状態の書き込みは行いません。メインの調整役はユーザーの制約と実現可能性を確認し、受け入れたタスクを記録して、計画を二重に作らず実行します。計画に依存する作業は `depends_on` で受け入れ済みの調整タスクにひも付けます。担当範囲やファイル割り当ての小さな調整はメインが処理し、方針に大きく影響する変更だけを coordinator に戻します。技術設計は architect、仕事の組み方は計画担当の coordinator が決めます。終了済みセッションを待ち続けず、必要に応じて範囲を定めた新しい調整タスクを使います。指定どおりのモデルや推論強度が利用できない場合は、その不足を報告し、計画に依存する作業を保留します。独立した許可済みの作業は続けられます。復旧時は計画担当を待ちません。

<a name="user-model-policy-27-october-2026"></a>

## ユーザーのモデル方針（2026 年 10 月 27 日）

ワークフローの役割で使えるモデルは `gpt-6.1-sol`、`gpt-6-astra`、`gpt-6.1-terra` のみです。推論強度は `medium` 以上とし、どの役割でも `none`、`minimal`、`low` は使用できません。役割ファイルでモデルと既定の推論強度を固定します。自動フォールバックやモデルの置き換えは行いません。廃止した `astra_coordinator` の役割を復活させてはいけません。統合された `limit_watcher` 役は `gpt-6.1-terra`／`medium` の組み合わせだけを使います。メインクライアントのモデルと推論強度を決めるのはユーザーです。このスキルが選択または変更することはありません。
