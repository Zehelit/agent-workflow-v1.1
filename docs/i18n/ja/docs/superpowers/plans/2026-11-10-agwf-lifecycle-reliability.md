# 起動から復旧までのライフサイクル実装計画

> 2026 年 11 月 10 日付の過去の実装計画です。チェックリストは当時提案された作業を記録しています。ここに記載された許可や非公開の成果物は当時の作業に属します。現在の動作は [運用仕様](../../../skills/agent-workflow-v1-1/references/operations.md) を参照してください。

<a name="goal-and-constraints"></a>

## 目的と制約

この計画では、初回起動の安全な再試行、期限内の計測更新、検証を伴う復旧、正常終了を扱いました。固定済みの候補パッケージ、型を持つワークフローコア、モデルを使わない監視処理は維持する方針でした。ライフサイクルの検証ツールでは、事前準備、実ホストでの観測、操作、終了を分離し、時間を計るテストは明示的に選ぶモードとする予定でした。[当時の仕様書](../specs/2026-11-10-agwf-lifecycle-reliability.md) も参照してください。

当時の計画では v1.1 に関係するソースのコミットとプッシュが許可されていました。GitHub Release やリリースタグの作成は対象外でした。Python 3.11 以上、標準ライブラリと unittest、既存の Codex ゴール・使用量ツール、Windows のプロセスとファイル共有の挙動を前提としました。進行中の作業、以前のランタイム証跡、パッケージのひも付けは保持する方針でした。既存のパッケージ、ゴール、計測、ユーザーの実際の発言、プロセスの識別情報は観測が必要でした。合成データは分離したテストに限りました。観測記録の期限切れ、実際の使用枠、早期予備枠、ユーザーによる停止には、それぞれ別の権限条件がありました。通常運用で人為的な SAVE は発生させず、他のセッションの作業やユーザーのモデル設定には手を加えない方針でした。

<a name="review-focus"></a>

## レビューで確認する点

1. 初回起動が失敗し、実際に使用量の観測期限切れで SAVE した場合は、補助プロセスの状態がまだ存在しなくても、条件を満たせば再試行できること。
2. 使用枠による停止、ユーザーによる停止、新しいゴール、識別できないワーカーは、技術的な復旧確認を通過しないこと。
3. 途中まで起動した状態や同時起動は、裏付けのある証跡で解決するまで不確定のままとすること。
4. 観測記録のファイルが新しくなっても、観測時刻は新しくならないこと。サンプルが新しくてもリースは期限切れになり得る。
5. 到着が遅れたネイティブイベントはタイミングの判定に合格しないこと。Windows の一時的なファイル共有エラーは、ワーカー終了の証拠にならない。

<a name="task-1-retry-a-failed-first-activation"></a>

## タスク 1. 初回の有効化に失敗したときの再試行

予定していたインターフェースは `activation_identity(command: str, payload: dict) -> dict`、`record_activation_attempt(runtime, record: dict) -> None`、`startup_retry_options(runtime, engine, command: str, payload: dict) -> tuple[str, ...]` です。実行ごとの `activation-attempt.json` にソースの識別情報、`schema_version`、`command`、`pre_state_sha256`、`phase`、観測した監視結果と失敗の詳細を記録します。`prepared`、`failed`、`committed` は別のフェーズです。`prepared` のまま残った記録は、実際の状態と突き合わせて解決する必要があります。

- まず古い観測記録で失敗を実証し、次に同じゴールで新しく計測して `bind-active-goal` と `activate` の再試行を確認する。元の SAVE のハッシュとユーザーの権限を保持し、ワーカーの正常性とアクティブ状態を確認する。
- `preflight_activation` の後で起動の意図を永続化する。コマンド、実行、ゴール、スレッド、範囲、目的、権限を結び付ける。観測時刻が新しくなっただけで新しい範囲は作らない。
- ランチャーとコアの処理の間に、この実行が所有する単一書き込み用のライフサイクルロックを使う。ロックの所有者が分からない場合は拒否する。ネイティブ UI と Python の状態は別の操作で扱う。
- 技術的に新しいエポックを開始するのは、同じ実行で `usage_receipt_expired` が確認され、アクティブなゴールの新しい観測と実際の使用量記録がそろった場合に限る。呼び出し側が再試行フラグを設定しても、それ自体は権限にならない。ワーカーの正常性とコア側の状態確定後に成功を記録する。
- 使用枠、早期予備枠、別の診断、新しい SAVE、ユーザー停止、変更されたゴールや非アクティブなゴール、稼働中または識別できないワーカー、変更済みまたは未完了のジャーナル、不正なパッケージ、同時起動が拒否されることを確かめる。不正な再試行用記録からの復旧も試す。ロールバックは該当する失敗範囲に限って確認済みの旧制御状態を戻し、それより新しい SAVE は保持する。
- 候補パッケージの共存とネイティブ観測記録のテストを実行する。アクティブ状態、現在の識別情報と鮮度、保持された履歴、実際のワーカーの後片付けを確認する。

<a name="task-2-prepare-before-measuring-and-refresh-early"></a>

## タスク 2. 計測前に準備し、余裕を持って更新する

検証ツールには `prepare`、`run --input PATH`、`observe --input PATH`、`close` を用意する予定でした。準備では、起動前にパッケージ、固定情報、役割、コマンドを確認します。`refresh_by(at: float, interval: float) -> float` は `at + interval - min(15, interval / 4)` を更新の目安として返します。間隔が 60 秒なら目安は 45 秒です。実際の期限は変わりません。

- 準備とヘルプには実データが不要で、古い入力や入力の欠落でアクティブ状態が作られず、再送しても観測時刻が変わらないことをテストする。
- 準備の後でネイティブゴールと利用量を取得する。実際の二つの利用枠とリセット時刻など、許可済みフィールドのみをコピーする。アカウント、本人識別、クレジットのデータは含めない。
- `sample_at`、`next_check_at`、`check_interval_seconds`、`refresh_by` を区別する。観測記録の保存やハートビートが成功しただけでは、観測が新しく監視が正常であるとは言えない。
- `status.at == usage.observedAt`、実行中のプロセスとの識別情報の一致、エポックの一致、`sampleFresh` と `leaseValid` を必須とする。入力を反映した後に更新を確認する。中断できない呼び出し中も観測記録を新しく保てるとは約束しない。
- 通常作業ではタイマーを注入しない。指示があればスナップショットを検証し、正常終了では完了とワーカー終了を両方確認する。人為的な SAVE ラッチが正常終了で生じなかったことを調べる。
- 観測記録の時刻と保存時刻を違え、ライフサイクルとネイティブ観測記録のテストを行う。

<a name="task-3-diagnose-timing-without-confusing-late-events-with-success"></a>

## タスク 3. 遅れたイベントを成功扱いせずタイミングを診断する

- `timed-test` は、明示的に依頼された場合に限り、事前準備済みで正常なワーカー、実際のイベント、`--event-input PATH --delay-seconds 10 --tolerance-seconds 1` を使って実行する。当時の目標時刻は `event_at + 10` で、待機には単調増加時計を用いる。
- 45 秒遅れて観測されたイベントは `INVALID_TIMING` を返すこと。当時の 98.74 秒と 45.05 秒の試行は失敗の記録として保持する。
- 既存の公式なゴールの証跡を使う。サポートされているネイティブイベントのフックがなければ、遅延または不完全な観測として扱う。UI を計測するために非公開の通信経路や認証情報ストアを使わない。
- `native_event_at`、`observed_at`、`worker_healthy_at`、`save_requested_at`、`save_returned_at`、`snapshot_verified_at`、`helper_halted_at`、`native_paused_at` をそれぞれ記録する。9〜11 秒の成功範囲は、事前に正常だったワーカーで SAVE を要求する時刻に適用する。ネイティブ側の一時停止には別の証跡が必要。
- 実環境での 2 回の試行で同じゴールと実行を使う。アクティブ状態、チェックポイント取得、停止の順で実証し、その後に条件を満たす実際の再開を確認する。初期状態のひも付けだけでは再開成功にならない。
- 合成した早着、遅着、再送、変更済みのイベント、停止の観測がない場合、明示的な停止、2 回の試行をテストする。実環境でのタイミング計測は任意とし、通常の受け入れと分ける。

<a name="task-4-verify-recovery-and-regressions"></a>

## タスク 4. 復旧と回帰を検証する

- 初回起動、初回試行中の期限切れと新しい計測での再試行、稼働中の期限切れから停止・スナップショット・停止確定・再開まで、不正な再試行の後の正しい再試行、ネイティブの一時停止からアクティブへの再開、自然な完了を確認する。該当するソース版とパッケージ版のエントリーポイントを試す。
- 作業再開前に `halted` を観測し、スナップショットを検証する。再開後は元のゴールと実行、新しいエポック、保持した SAVE のハッシュ、権限、実際のワーカーの正常性を確認する。
- 使用枠、早期予備枠、それより新しい使用枠の SAVE、ユーザー停止、別のゴール、期限切れまたは再送の観測記録、破損したチェックポイント、稼働中の子プロセスが未解決の場合は拒否する。ネイティブの `blocked` には独自の基準を適用する。
- Windows のテストでは実行が所有する必要なファイルだけをコピーし、既知のプロセスの識別情報とターミナルの正常性を確認する。一時的な共有エラーからプロセスの終了を推定しない。権限エラーが続く場合は、定めた時間内に表面化させる。
- 個別ケースが通った後、リポジトリの二つのテスト群を実行する。件数は今回の実行結果から確認する。正常な実ライフサイクルでは、本物のゴールと事前準備済みの検証ツールを使う。期限切れと時間診断は個別の許可が必要で、`not_tested` のままとなる場合がある。

<a name="task-5-document-the-contract-and-verify-distribution"></a>

## タスク 5. 仕様を文書化し、配布物を検証する

- 初回の再試行、停止後の再開、使用枠とユーザー停止それぞれの経路を文書化する。観測とリースを更新する順序、遅延イベントの診断で分かることを説明する。
- パッケージと既存作業の一覧を確認する。編集内容と稼働中のインストールを保持する。過去の固定情報の所有関係から稼働を推定せず、実行中の処理を移行しない。
- 同じソースから 2 回ビルドし、マニフェストと ZIP のハッシュを比較する。変更した同梱ファイルはビルドとインストールのテストで検証する。一時的なパッシブ実行でインストール済みの候補を調べ、固定情報と Windows のアクセスを検証し、その受動的な検証範囲を報告する。
- `startup_retry`、`receipt_refresh`、`halted_resume`、`native_continue`、`natural_complete`、`timed_test`、`worker_exit`、`package_match` はそれぞれ証跡を記録する。過去の否定的な結果も保持する。
- 当時許可されていたソース公開に先立ち、権限、ロールバック、SAVE の保持を確認する。非公開の報告、観測記録、ランタイム状態は Git の外に置く。

<a name="task-6-align-the-existing-v11-identity-and-presentation"></a>

## タスク 6. 既存の v1.1 の識別情報とリポジトリの見せ方をそろえる

- 表示名、呼び出し名、パッケージのパス、新しい名前空間を一緒に移行する。過去のランタイム識別情報と受け入れ済みの固定情報は保持する。
- 実際の v1.0 の履歴と v1.1 の変更を `CHANGELOG.md` に記録する。README では目的、制約、アーキテクチャ、ワークフロー、役割の調整を説明する。
- クリーンなチェックアウトから固定情報を保持したまま検証し、明示的な呼び出しへ進むまでの、人とエージェントそれぞれのインストール手順を書く。セットアップそのものはネイティブゴールを開始せず、モデル設定も変更しない。
- 当時許可されていた公開では、About とトピックをソースに合わせる。リポジトリのアクセス権とブランチ保護を保持する。README のコマンドと、図がソースどおりであることを検証する。
- 許可されたファイルだけを公開し、リモートのコミットとツリー、バージョン、文書を検証する。リリースやタグを作成していないことも確認する。

<a name="acceptance-boundary"></a>

## 受け入れ範囲

当時の計画では、最終の公開作業に先立って、コアのタスク 1〜5 を行う順序でした。初回再試行と実際に停止した後の再開の各ケース、回帰テスト、パッケージの検証、対象範囲が明確な実観測を求めました。ネイティブ UI の挙動には実ホストからの証跡が必要でした。10 秒のタイミング結果は独立した主張であり、実際のネイティブイベントと、別途観測した時刻が必要でした。
