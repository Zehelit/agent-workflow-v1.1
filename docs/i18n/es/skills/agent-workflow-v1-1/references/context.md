# Contexto actual selectivo (N06)

`tools/render-active-run.py` lee un proyecto desechable o seleccionado de forma explícita en el código fuente o la skill instalada. No activa, renueva, migra ni escribe el estado. Proporciona mediante `--as-of` la hora real de observación, sin sustituir la de creación de la fuente o del turno original. El contrato JSON estable es `context_version: 1`. Las mismas entradas, referencias, estado y hora producen el mismo resultado.

El resumen contiene objetivo, identidad actual, autorización o vínculo nativo exacto, las fechas originales, la observación de objetivo vigente, contratos de tareas abiertas, dependencias y revisiones fijadas, observaciones de ejecución y aceptación, impedimentos y pruebas en contra, hashes de archivos cambiados, referencias de evidencia y próximo paso. Omite recibos completos, instrucciones preparadas, informes completos, texto final, transcripciones y registros de herramientas. Los contratos ya aceptados siguen en el estado original fijado, y la vista abreviada muestra su aceptación y las referencias precisas.

Las referencias son una lista JSON estricta de objetos `{path, sha256, kind}` con `task_id` opcional. `kind` es `evidence`, `decision` o `counterevidence`. Los archivos deben ser rutas exactas y seguras relativas al proyecto. SHA-256 usa el valor completo en minúsculas. Los informes se quedan en sus archivos. La prueba en contra sigue bloqueando hasta que el agente principal decida generar otro manifiesto con otra revisión. Abreviar el resumen no la borra. Hashes ausentes o vencidos, referencias sin fijar no soportadas, falta de prueba terminal, dependencias pendientes o invalidadas, trabajo rechazado o incierto y observaciones obsoletas de objetivos, inventario o uso se muestran como bloqueos. Se rechaza el estado malformado, las dependencias ausentes y valores de fijación inválidos.

Para usar el resumen protegido, fija el propio JSON de referencias como entrada inmutable `file_inputs`. `prepare.current_context` contiene exactamente `{path, sha256, manifest_path, manifest_sha256}`. El ayudante coteja el manifiesto con la entrada tipada, lo lee de forma independiente y vuelve a generar la vista desde el estado actual y la procedencia original. Compara todo el resultado. Volver a fijar un resumen acortado no elimina un bloqueo ni convierte una cita antigua en nueva. La edad admitida es de 0 a 60 segundos. Preparar cambia el estado, por lo que se vuelve a generar el resumen con el mismo manifiesto antes de `dispatch-start`. Se rechaza omitirlo o sustituir el manifiesto. Siguen decidiendo los controles de autorización, uso, identidad nativa, capacidad, parámetros preparados, revisiones y hashes. `dispatch_authorized` es siempre falso en el resumen.

Los comandos que no usan `current_context` mantienen la lectura directa. La vista no concede permiso para herramientas nativas. El agente principal verifica los recibos reales y la autorización original. Los hashes prueban igualdad de bytes, no identidad del proveedor. Las observaciones de archivos no son una instantánea atómica contra escritores externos.

`cache_status` sigue en `unknown` y `token_measurement` en `pending_N08`. La selección de contexto es un contrato del código. No se ha demostrado con él la reconstrucción real en otro subagente, ahorro de caché o tokens ni adopción instalada. Usa las fuentes para reconstruir el estado útil y conserva objeciones de revisión.

<a name="execution-and-acceptance-n07"></a>

# Ejecución y aceptación (N07)

`status.task_observations` es una vista de solo lectura de schema2 con `contract_version: 1`. Incluye por tarea revisión, ejecución observada con sesión, hora y vigencia, aceptación, base de aceptación, identidad del revisor y derechos de escritura. La ejecución sin observación vigente se considera desconocida. El estado nativo done, idle o stopped libera capacidad de ejecución al calcular el inventario actualizado, sin aceptar archivos. Una aceptación independiente pendiente mantiene la asignación de escritura del productor. El máximo opcional de sesiones abiertas se calcula por separado.

El verificador fija la revisión y los hashes exactos del productor que ya no escribe. El revisor no puede depender directa o indirectamente de que ese productor sea primero aceptado, porque observar para revisar y exigir una dependencia aceptada son relaciones diferentes. El productor sigue pendiente durante la revisión. La aceptación registra el verificador en el campo ya soportado `review` y comprueba sesión distinta, revisión objetivo, contrato de entrada y hashes exactos. Cambiar revisión o bytes invalida la revisión; restaurar los bytes antiguos no la hace válida de nuevo. Una aceptación schema2 antigua sin vínculo al revisor se muestra como `historical_unrecorded` y no se declara independiente retrospectivamente.

La independencia exige sesiones nativas de productor y revisor distintas y no vacías, con hashes asignados y anotados que coincidan. Es la misma condición para la vista y para las dependencias aceptadas. La aceptación histórica incompleta se lee como `historical_unrecorded`, pero no permite preparar, registrar ni iniciar un envío que dependa de ella. El resumen incluye `DEPENDENCY_NOT_ACCEPTED`. Perder el vínculo del revisor o la identidad nativa después de preparar también bloquea el envío. No se inventan o migran identidades antiguas.

Es una vista adicional que usa un campo opcional existente. Schema2 no cambia. Se rechazan formatos anteriores y no se importan. La autorización actual y el vínculo aceptado siguen decidiendo; el resumen no los inicia ni sustituye.

# Comprobación previa al traspaso del productor

`tooling/check-producer.py` es un control desde el código fuente. Ejecútalo en una copia de trabajo con Python incluido, `-X utf8 -B`, en modo normal y con `-O`. Requiere las pruebas del repositorio y no es un comando del paquete instalado. Indica las rutas cambiadas y la API compartida. Los selectores reutilizan regresiones del núcleo, entradas, autorización, objetivos, coordinación, contexto y aceptación, y contraejemplos A04/A09/A11. El ejecutor histórico A11 se revalida en memoria contra el hash del flujo candidate en una copia temporal. Sus bytes originales se conservan y se reportan ambas dependencias fijadas. Este control no ejecuta toda la suite del monitor o el navegador.

El resultado fija la unión de entradas definidas del candidate (fuente, pruebas y roles) y archivos declarados como cambiados, también Markdown fuera de la lista fija. Deben ser archivos existentes de rutas normalizadas relativas, sin escapes, rutas absolutas o de unidad, alias o enlaces. Se calculan los hashes de toda la unión antes y después. Si cambia un archivo declarado no hay PASS. `--expected-pins` debe identificar la unión completa. Se guardan selectores, cantidades, fallas y estabilidad del código. Siempre informa `independent_acceptance: false`. Falla de prueba, selector ausente, pin alterado o metadatos de rechazo inválidos impiden el PASS del productor. Tras terminar el productor se realiza una revisión independiente del resultado importante.

Los metadatos opcionales de rechazo tienen solo `rejections` y `rework_seconds`. Si faltan, la lista de rechazos observados queda vacía y el costo es desconocido. Cada rechazo anota ID y clase del defecto, referencia para reproducirlo, corrector y revisor específico, revisión y hashes del código. Quien corrige no se revisa a sí mismo. Un segundo rechazo de la misma clase incluye `root_plan_correction` breve. El agente principal decide el plan, nombra un corrector y solicita otra revisión independiente. No añade automáticamente arquitecto ni equipo.
