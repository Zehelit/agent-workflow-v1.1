# Codex 사용량 측정 기록

명시적으로 승인됐고 활성화된 AGWF 실행에서만 사용하세요. 현재 스킬을 명시적으로 호출하면 그 범위의 실행을 시작해야 합니다. Codex 목표 생성이 금지됐으면 [운영 안내서](operations.md)의 수동 감시를 사용하세요. 패키지를 업데이트하거나 스킬을 논의하거나 사용량을 공개하는 것만으로 비활성 워크플로가 다시 켜지지 않습니다.

주 에이전트가 기존 Codex 연결로 `mcp__codex_app__get_usage_limits`를 호출합니다. Python은 두 번째 애플리케이션 서버를 열거나, 다른 CLI를 선택하거나, 인증 파일을 읽거나, 비공개 전송 경로에 연결하거나, 모델을 호출하지 않습니다. 백그라운드 프로세스는 전달된 측정 기록을 확인하고 유효 기간을 검사합니다. 작업 경계에서 호스트 도구를 호출하는 일은 주 에이전트의 몫입니다.

실제 도구 결과로 비공개 입력 JSON을 만드세요.

```json
{
  "source": "mcp__codex_app__get_usage_limits",
  "sourceId": "actual-tool-call-receipt-id",
  "observedAt": 1800000000,
  "result": {
    "rateLimits": {
      "limitId": "codex",
      "primary": {"usedPercent": 25, "windowDurationMins": 300, "resetsAt": 1800010000},
      "secondary": {"usedPercent": 30, "windowDurationMins": 10080, "resetsAt": 1800600000}
    }
  }
}
```

숫자는 예시입니다. 실제 관측 시각, 기록 식별자, 값을 보존하세요. 값을 만들어 내거나 관측 시각을 파일 게시 시각으로 바꾸지 마세요. 실제 결과에 여러 종류의 한도가 있으면 `rateLimitsByLimitId.codex`를 우선 사용하세요. 여러 한도 맵이 있는데 Codex 항목이 없으면 조용히 다른 한도를 쓰지 않고 거부합니다. 두 구간의 길이와 초기화 시각이 모두 필요합니다. 비공개 입력에는 필요한 한도 필드만 복사하세요. 계정, 프로필, 크레딧 필드는 필요하지 않습니다. 저장되는 `watcher/usage-source.json`에는 허용된 구간 필드, 관측 및 출처 식별자, 실행과 실행 세대 연결 정보만 남습니다.

`workflow activate --input AUTH.json --usage-input USAGE.json`과 `bind-active-goal`은 작업 프로세스를 시작하기 전에 권한을 검증합니다. `resume`도 `--usage-input`으로 새 기록을 받아야 하며 이전 세대 기록은 재사용할 수 없습니다. 수동 `watcher start --usage-input USAGE.json`에도 같은 입력 사전 검사가 적용됩니다. 기록이 누락됐거나 이미 만료됐으면 프로세스를 만들기 전에 거부합니다.

작업 중 새 기록을 반영하려면 `watcher ingest --usage-input USAGE.json` 또는 워크플로·조율 명령의 `--usage-input`을 쓰세요. `ingest`는 워크플로를 활성화하거나 프로세스를 시작하거나 권한을 갱신하거나 SAVE 중단 표시를 지우지 않습니다. 새 입력 파일이 들어오면 이전 기한을 기다리지 않고 평가합니다. 해당 프로세스가 새 값을 읽는 동안 상태 출력에 이전 평가가 잠시 남을 수 있습니다. 중요한 배정 전에 최신 정상 상태를 확인하세요.

주 에이전트는 최대 300초인 적응형 기한 전에 실제 측정값을 갱신합니다. 임계값 근처이거나 사용량이 빠르게 늘면 기한은 짧아집니다. 프로세스가 이전 파일을 다시 읽어도 새 측정으로 표시하지 않습니다. 주 에이전트가 데이터를 얻지 못하면 한 번 더 검증한 뒤 SAVE_AND_STOP을 고정합니다. `usage_receipt_expired`가 기록됐다면 동일한 승인된 활성 목표에서 `workflow resume`과 `usage_recovery: true`로 재개할 수 있습니다. [기술 복구](operations.md#expired-telemetry-recovery-under-existing-authority)를 참조하세요. 새 기록만으로는 중단 표시가 해제되지 않지만, 이 검증된 복구는 새 사용자 메시지를 요구하지 않습니다. 실제 한도 소진이나 사용자의 명시적 중단에는 해당 재개 조건이 적용됩니다. 다음 도구 호출에 걸릴 시간을 고려해 작업 경계에서 갱신하세요. 기한까지 기다리라는 뜻이 아닙니다. 중단할 수 없는 긴 호출 동안에는 갱신이 어렵고 백그라운드가 기본 도구를 알아서 호출한다는 보장은 없습니다.

잘못된 입력, 다른 실행이나 실행 세대, 미래 및 만료 관측, 역행하는 시각, 내용을 바꿔 재사용한 기록을 거부합니다. 동일한 측정 기록을 다시 게시하면 상태가 바뀌지 않습니다. 다른 Codex 기록과 마찬가지로 시각과 출처는 호출자가 제공한 근거입니다. JSON 구조만으로는 공급자를 인증할 수 없습니다. 원본 근거는 비공개로 보관하고 임의의 출처 이름을 독립된 증거로 취급하지 마세요.

측정 실패 시 측정값과 상태에는 허용 목록에 있는 `diagnosticCode`와 오류 클래스가 표시됩니다. `watcher/diagnostics.json`에는 구조화된 항목을 최대 20개 남깁니다. 예외 본문, 인증 데이터, 임의의 도구 본문은 제외합니다. 예상하지 못한 Python 프로세스 오류는 로컬 `worker-stderr.log`에 남습니다. 하위 서버가 없어졌으므로 그 표준 오류를 버리는 일도 없습니다.

모든 후보 명령과 감시 프로세스 평가 시 새 입력을 포함해 패키지 전체 무결성을 검사합니다. 상태 신호는 실행과 실행 세대의 제어 정보만 검사하고 상태를 게시합니다. 매 신호마다 패키지를 순회하거나 다시 해시하지 않습니다. 바뀐 의존성은 다음 측정이나 명령에서 거부합니다. 모든 신호에서 발견된다고 보장하지는 않습니다.

단위 테스트는 실제 측정 파일 쓰기와 읽기, 엄격한 JSON, 만료와 재사용 및 식별자, 임계값, 제한된 진단, 측정 경로에서 프로세스가 생성되지 않는지를 확인합니다. 실제 Remote 제품 검증은 별도입니다. 사용자가 명시적으로 다시 켤 때까지 설치된 워크플로는 비활성 상태를 유지하세요. 유지보수 중에 합격 근거를 만들어 내기 위해 실제 AGWF 프로세스를 시작하지 마세요.
