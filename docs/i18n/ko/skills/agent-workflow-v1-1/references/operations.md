# 운영

Python 3.11 이상과 표준 라이브러리만 필요합니다. `python -X utf8 -B scripts/candidate.py --help`로 도움말을 확인하세요. 시작 전에 [런타임 연결](coexistence.md)을 읽고 외부 빌드 기록에 있는 매니페스트 SHA를 보존하세요. `python`이 없으면 호스트에 포함된 Python을 사용하세요. 명령은 `--input path`나 표준 입력으로 JSON을 받습니다. 상태는 `<project>/.agent-workflow-v1-1/runs/<run-id>/state.json`에 있습니다. 체크포인트, 잠금, 임시 데이터, 감시 프로세스 소유권, 조율 저널은 같은 격리 실행 이름 공간에 두고 주 에이전트만 여기에 씁니다. 파일, 테스트 산출물, 스냅샷을 일반 프롬프트 입력으로 넣지 않습니다.

<a name="start-and-dispatch"></a>

## 시작과 작업 배정

명시적 호출이 들어오면 준비 작업이나 작은 작업도 본격적으로 시작하기 전에 같은 턴에서 실행을 시작해야 합니다. 지침을 읽는 것만으로 시작되지 않습니다. Codex 목표 생성이 승인 범위 밖이면 수동 감시를 사용하세요. 목표나 연결 근거를 꾸며 내지 마세요. 스킬을 논의하거나 유지보수한다고 정지된 일을 재개하지 않습니다.

활성 워크플로 밖에서 작업하려면 새 실행 ID를 고른 뒤 고정 후보의 `watcher start --usage-input USAGE.json`을 사용하세요. 감시만 시작하며 워크플로를 활성화하거나 에이전트를 승인하지 않습니다. `watcher status`로 최신 정상 측정값과 이 실행 및 실행 세대에 속한 실제 작업 프로세스가 확인되거나 거부가 보고될 때까지 확인하세요. 이후 실제 사용량 기록은 `watcher ingest`로 반영하고 작업 경계에서 `watcher renew`로 실행 유지 기한을 갱신합니다. `watcher stop`으로 끝내고 종료를 검증하세요. 해당 범위의 정상 실행이 이미 있으면 재사용합니다. 중단 상태라면 승인된 계속 절차와 새 실행 세대, 모든 복구 검사가 필요합니다. 중복 프로세스로 중단을 우회하지 마세요. 요청된 일을 하기 전에 관측된 시작 결과를 보고하세요. 시작 실패나 `SAVE_AND_STOP`이 나오면 사유를 알리고 본 작업을 보류합니다.

활성화나 재개 전에 [Codex 사용량 기록](native-usage.md)을 읽으세요. 주 에이전트가 기존 `mcp__codex_app__get_usage_limits`에서 얻은 현재 측정값을 `--usage-input`으로 제공하며 백그라운드 프로세스는 이를 읽습니다. 감시 프로세스는 Codex 애플리케이션 서버를 여는 일이 없으며 기본 도구를 스스로 호출할 수 없습니다. 적응형 기한이 오기 전에 실제 새 기록을 얻으세요. 기존 기록을 재사용해도 관측 시각은 갱신되지 않습니다. 기록이 없거나 만료됐거나 재사용됐거나 다른 실행에서 가져왔으면 작업을 멈춥니다. 수동 감시 시작에도 갱신 규칙이 적용됩니다. `watcher ingest --usage-input PATH`는 데이터를 반영할 뿐 프로세스를 시작하거나 AGWF를 다시 활성화하지 않습니다.

1. `validate`는 정의를 확인합니다. `activate`는 `objective`, 아래의 타입 지정 승인 근거, `models`(관측한 모델별 추론 강도 목록), `slot_limit`(주 에이전트를 포함한 전체 활성 슬롯), `inventory`(실제 하위 에이전트 ID와 상태), `observed_at`(Unix 시각), 선택적인 `session_limit`을 받습니다. 가용성 근거를 꾸미지 마세요. 활성화는 주 채팅 모델 설정을 지정하거나 보고하지 않습니다.
2. 고정 후보는 승인된 `activate` 또는 `bind-active-goal`에서 내부 감시 프로세스를 시작하며 활성 상태를 기록하기 전에 첫 정상 측정값을 확인합니다. 유효한 `resume` 뒤에는 새 실행 세대를 엽니다. 활성 워크플로·조율 호출은 600초 실행 유지 기한을 연장합니다. 작업 간격이 길어지는 지점에서 `workflow status`를 실행해 기한과 상태를 확인하세요. 실행 유지 기간이 끝나거나 측정 상태가 정상적이지 않으면 새 작업은 거부되고 복구 명령은 계속 쓸 수 있습니다. `complete` 및 `halt`는 중단을 요청한 뒤 실제 종료를 확인합니다. 수동 `watcher start/status/renew/stop`은 새 실행 ID로 진단 및 활성 워크플로 외부 작업에 사용합니다. 명시적 선택 시 주 에이전트가 적절한 시작 절차를 수행하고 검증합니다. Codex 자동 시작 연결은 설치되지 않습니다. 오래된 측정과 복구에는 내부 고정 감시 역할 정책을 따르세요. 감시 프로세스는 모델을 호출하거나 현재 채팅을 제어하지 않습니다. 일반 한도 확인은 에이전트를 시작하지 않습니다. `usage-due`는 `REUSE_MEASUREMENT` 또는 `READ_USAGE`를 반환합니다. 상당한 작업이나 병렬 작업 전에 `substantial_work: true`로 새 도구 측정을 요구하세요. `usage`는 `observed_at`과 실제 도구의 원시 `rateLimits`를 받습니다. 두 구간이 모두 필요합니다. 값이 없으면 한 번 더 시도하고 여전히 없으면 복구에 들어갑니다. 잔여량이 40% 초과, 25% 초과, 20% 초과, 20% 이하일 때의 기한은 각각 300/120/60/30초입니다. 구간별 소모 속도로 계산한 잔여 20%까지의 예상 시간의 4분의 1이 더 짧으면 기한을 그만큼 줄입니다. 초기화된 값이나 오래된 값으로는 소모 속도를 정하지 않습니다. 잔여량 25% 이하 또는 예상 10분 이하이면 `CHECKPOINT_SOON`이 완료된 작업의 검증된 체크포인트를 요구합니다. 메시지마다 갱신하지 말고 파일 쓰기 묶음이 끝났을 때 갱신하세요. 20% 이하 또는 그 임계값까지 예상 120초 이하이면 `SAVE_AND_STOP`이 배정을 차단하고 조기 복구를 시작합니다. `prepare`는 적응형 기한이 지난 측정값을 거부합니다. 유휴 시 조회하지 않습니다. 멈출 수 없는 호출이나 다른 채팅의 갑작스러운 소모를 추정으로 막을 수 있다고 보장하지 않습니다.
3. `task`는 `id`, `role`, `objective`, `file_inputs`, `context_refs`, `review_targets`, `criteria`, `writes`(삭제할 파일을 포함하는 정확한 프로젝트 상대 경로), `depends_on`, `independent_review`(불리언)를 받습니다. 읽기 전용 작업에는 빈 쓰기 목록을 사용하세요. 디렉터리 전체를 쓰기 경로로 지정할 수 없습니다. 배정 전에 `inventory`로 실제 하위 상태를 갱신합니다.
4. `prepare`는 작업 `id`와 선택적 `effort` 및 고정 `current_context`를 받습니다. 모델, 사용량, 슬롯, 의존 관계, 파일 해시를 확인하고 슬롯을 예약한 뒤 `fork_turns: none`을 포함한 실제 `collaboration.spawn_agent` 인자를 반환합니다. 메시지에는 배정된 역할의 `SKILL.md`와 `MEMORY.md`가 들어갑니다. 문서가 없거나 비어 있으면 로드를 거부하며 모든 문서는 패키지 매니페스트에 포함됩니다. 인자를 그대로 사용해 호출하세요. 이어서 `record`에 `id`, `session_id`, `submitted_arguments`, `receipt`(실제 도구 결과), 관측 메타데이터가 있으면 `effective_model`과 `effective_effort`를 전달합니다. 실패나 불확실한 호출은 `certain_not_started`를 사용해 `dispatch_failed`에 기록합니다. 불확실한 세션은 실제 목록과 대조할 때까지 후속 작업을 차단합니다. 결과를 모르는 시작을 무작정 재시도하지 마세요.
5. `finish`는 `id`, `accepted`, `evidence`, 독립 검토가 필요한 경우 `review_task`를 받습니다. 먼저 `inventory`로 세션이 idle, stopped 또는 done인지 확인하세요. 파일 쓰기 중에는 소유권을 풀지 마세요. 검토자의 `review_targets`에 검토할 작업 ID와 리비전을 지정합니다. 작성자가 쓰기를 멈춘 뒤 검토가 끝날 때까지 승인은 대기 상태입니다. 검토 중 산출물 해시는 바뀌면 안 됩니다. 거부된 작업은 거부 상태로 남습니다. 원인을 해결하고 새 작업을 만드세요. `cancel`은 `id`와 `reason`을 받아 준비됐지만 배정된 적 없는 작업을 해제합니다. 주 에이전트는 통합 전에 사용자 작업을 확인합니다. 결과를 알 수 없는 외부 조치는 재시도 전에 실제 상태를 확인합니다.

모든 워크플로 역할은 `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6.1-terra`와 최소 `medium` 강도만 쓸 수 있습니다. 역할 파일이 모델과 기본 강도를 고정하며 자동 대체는 없습니다. 주 채팅에는 사용자가 고른 클라이언트 설정을 사용하고 패키지는 실행 중인 모델을 바꾸지 않습니다. 후보가 준비한 배정 인자는 고정된 역할 설정을 그대로 유지합니다. 폐기된 `astra_coordinator`는 쓸 수 없습니다.

감시 역할은 정확히 `gpt-6.1-terra` 및 `medium`을 사용합니다. 어느 역할에도 대체 모델은 없습니다. 활성화할 때 실제 관측한 모델과 강도의 가용성을 기록하세요. 정확한 역할 설정이 없으면 배정을 거부합니다.

## 복구와 중단

<a name="initial-activation-retry-v11"></a>

### 최초 활성화 재시도 (v1.1)

후보는 첫 활성화 전에 `activation-attempt.json`을 적고, 감시 프로세스가 정상적으로 시작되고 코어 상태가 반영된 뒤에만 확정 표시를 합니다. 실패 응답에는 `startup_retry.attempt_sha256`이 들어갈 수 있습니다. 실패 기록은 변경 가능한 실행 디렉터리 밖에 보관하세요. 실제 새 측정값, 같은 목표의 새 관측, 원래 승인 및 `--startup-attempt-sha256 PRESERVED_FAILURE_PIN`으로 같은 `activate` 또는 `bind-active-goal`을 재시도합니다. 편집한 저널 해시를 다시 계산해 승인으로 대신하지 마세요.

| 상황 | 지원되는 동작 |
|---|---|
| 최초 시작의 측정 만료를 기록했고 상태와 식별자가 그대로이며 프로세스가 없음을 확인함 | 외부 실패 해시와 실패 이후 새 관측 및 측정값으로 최초 명령 재시도 |
| 이미 중단 확정된 워크플로에 측정 만료가 기록됨 | 모든 중단 이후 확인을 거쳐 `usage_recovery: true`로 기존 `resume` 실행 |
| 한도 소진, 조기 중단, 사용자 중단, 다른 실패, 수정되거나 미완료 저널, 식별되지 않은 프로세스 | 우회 경로가 없습니다. 근거를 보존하고 해당 재개 또는 대조 규칙을 따릅니다. |

수명 주기 시작, 상태 확정, 롤백과 중단·승인 전이는 후보가 소유한 잠금을 공유합니다. 이유를 모르는 `lifecycle.lock`을 삭제하지 말고 실제 소유자와 끝나지 않은 동작을 확인하세요. Codex 기본 도구와 함께 원자적 트랜잭션을 구성하지 않습니다. 조율 배치는 순서대로 실행하고 저널을 쓰지만 전체가 원자적이지 않습니다.

Codex에서 측정하기 전에 준비하세요. 가능하면 `sample_at + interval - min(15, interval / 4)` 전에 갱신하세요. 이는 일찍 움직이기 위한 권장 시각이며 유효 기한을 늘리지 않습니다. 새 측정 시각, 실제 프로세스와 실행 세대, 상태 신호, 측정 최신성, 실행 유지 기한을 각각 검증합니다. 측정값을 반영하기만 해서는 실행 유지 기한이 연장되지 않습니다. 주간 예외에는 실제 사용자 발언과 한정된 만료 시각을 사용합니다. 코어와 감시는 같은 구간으로 판단하되 원본 관측 두 개를 모두 보존합니다.

<a name="initial-native-goal-binding-n02"></a>

### 최초 Codex 목표 연결 (N02)

Codex 목표가 이미 활성 상태이며 초기화에 사용자 출처의 유효 시간보다 오래 걸렸다면 `bind-active-goal`을 사용하세요. 작업, 작업 이력 필드, 중단·중단 확정·완료·마이그레이션이나 재사용 방지 예약이 없는 실제 초기 비활성 schema2 보조 프로그램만 시작할 수 있습니다. 기존 실행에는 현재 권한과 최신 앱 관측을 사용합니다. 중단 확정된 Codex 연결 실행은 중단 이후 `paused` 또는 `blocked`를 관측한 뒤 같은 목표의 더 최근 `active`를 관측해 재개할 수 있습니다. `updated_at`만 바뀌었다고 사용자가 상태를 바꿨다는 증거가 되지 않습니다. 목표가 계속 승인돼 있고 활성 상태에서 측정값만 만료됐다면 아래의 기술 복구를 사용하세요.

`native_binding`에는 `binding_id`, 목표·채팅·실행 ID, 새 ID가 있는 objective 범위, 정확한 Codex `objective`, 원래 `goal_created_at`, 현재 `observed_at`을 넣습니다. 명령의 `objective`도 정확히 같아야 합니다. 모델, 슬롯, 목록에 관한 일반 근거를 제공하고 별도 `app_goal_observation`에 일치하는 목표·채팅·본문·생성 시각·관측 시각, `status: active`, `source_kind: get_goal`, 실제 호출 기록 ID를 넣습니다. 관측은 미래가 아니어야 하며 60초 이내여야 합니다. 오래됐더라도 원래 목표 생성 시각을 유지합니다. 설명용 접두사를 덧붙이지 말고 정확한 목표 본문을 씁니다.

`interpretation`과 `procedural_check`는 주 에이전트가 각각 작성한 비어 있지 않은 근거입니다. 연결 전에 현재 승인 목표의 맥락과 이후의 사용자 제한을 확인합니다. 이전 중단, 보고서, 정책 메시지에서 연결을 도출하지 마세요. `exact_quote`, `source_message`, `original_turn_id` 또는 사용자 출처 생성 시각을 꾸며 내지 마세요. 동작 중이거나 상태가 불명확한 하위 에이전트가 남아 있으면 안 됩니다. 보조 프로그램은 전달받은 구조와 일관성을 점검하고, 주 에이전트가 실제 Codex 출처를 확보합니다.

별개로 관리하는 Codex 연결 기록과 재사용 방지 기록은 이후 사용자가 재개하거나 활성화해도 보존됩니다. 현재 근거가 Codex 연결이라면 모든 `app-goal` 갱신에 목표와 채팅의 식별자뿐 아니라 원래 생성 시각과 정확한 목표 본문도 넣습니다. 최신 사용량, 목록, 슬롯, 불확실성, 배정 검사는 계속 필요합니다. Codex 목표가 아직 활성 상태여도 보조 프로그램의 stop이나 halt는 유효합니다. 중단, 스냅샷, 중단 확정, 검증된 복구는 일반적으로 동작합니다. 측정 문제 이외의 중단 뒤 `resume`에는 중단 확정 뒤 직접 받은 `explicit_goal_continuation` 또는 `native_ui_resume: true`가 필요합니다. 후자는 중단 확정 이후 `app-goal`에서 `paused`나 `blocked`를 관측하고, 이어 같은 목표의 최신 `active` `get_goal` 기록을 얻어야 합니다. Unix `updated_at`은 stop과 halt보다 엄격히 뒤여야 합니다. 같은 초 안에서 순서를 알 수 없으면 재개를 거부합니다. 두 경로에서 모두 체크포인트·사용량·목록을 확인합니다. Codex 기록으로 누가 동작을 했는지는 알 수 없고 기록은 한 번만 씁니다.

<a name="expired-telemetry-recovery-under-existing-authority"></a>

### 기존 승인 아래의 측정 기록 만료 복구

`usage_receipt_expired`는 주 에이전트가 적응형 기한을 놓쳤다는 뜻입니다. 한도 소진을 증명하지 않습니다. 본 작업을 멈추고 저장하고 중단을 확정하세요. 고정 후보가 `halt` 중 같은 실행·세대에서 감시 프로세스가 본 실제 오류를 기록합니다. `usage_failure`를 직접 넘기지 마세요. 복구 전용 조율 배치는 stop과 snapshot을 할 수 있습니다. 수명 주기 `halt`와 `resume`은 후보의 직접 명령으로 남습니다.

이 원인이 기록되면 중단 확정 뒤 실제 Codex 사용량과 같은 활성 목표의 최신 `get_goal`을 얻고 해당 하위 목록을 갱신하세요. 체크포인트와 현재 파일의 해시, 프로세스 종료를 확인합니다. `workflow usage`와 `inventory`를 기록한 뒤 `workflow resume --input RECOVERY.json --usage-input USAGE.json`을 실행하세요. `RECOVERY.json`에는 `usage_recovery: true`와 `app_goal_observation`만 들어갑니다. Codex 연결 관측에는 원래 목표와 생성 시각을 유지합니다. 바뀐 `updated_at`, 비활성 관측, 꾸며낸 사용자 인용 또는 합성 클릭 기록은 필요하지 않습니다. 이 경로는 기존 승인을 사용합니다. 후보는 저장된 실패와 실제 감시 중단 표시가 여전히 같은지 검사한 뒤 새 실행 세대를 시작하고 감시 정상 상태를 기다립니다. 한정된 주간 예외와 과거 SAVE 기록은 보존합니다. 이전 작업은 거부되며 암시적으로 다시 시작하지 않습니다.

실제 한도·조기 중단, 누락·오류·그 밖의 측정 실패, 알 수 없는 원인, 다른 목표, 오래된 사용량, 비활성 Codex 목표, 실행 중이거나 식별되지 않은 하위 에이전트, 변경된 체크포인트, 승인된 계속 요청으로 해제되지 않은 명시적 사용자 중단은 이 경로에서 거부합니다. Codex 목표 상태를 바꾸면 안 됩니다. 사용자가 일시 정지 또는 차단된 목표를 Continue로 활성화할 수 있습니다. 실제 활성 관측을 얻고 같은 기술 검사를 적용하세요. 같은 목표가 활성 상태이면 일반 자동 목표 턴도 기술 중단을 복구할 수 있습니다. 측정 만료만을 이유로 다시 타이핑한 계속 요청을 받거나 `blocked`를 설정하지 마세요. Codex의 `update_goal` 절차를 따릅니다. 활성 상태의 시각으로 누가 클릭했는지 단정할 수 없습니다. 기록된 명시적 사용자 중단을 해제하는 것은 성공적으로 승인된 직접 계속 요청 또는 현재 Codex에 연결된 실행에서 검증한 기존 비활성→활성 UI 경로입니다. `usage_recovery`는 그러한 해제 이벤트를 제공하지 않습니다.

Codex 목표에 연결하지 않고 수동 감시만 한 실행은 워크플로의 `usage_recovery`를 사용하지 않습니다. 명시적 계속과 새 실행 세대 규칙을 따릅니다. 원인 기록이 없는 이전 버전의 중단 실행을 조용히 갱신하거나 명칭을 바꾸지 않습니다. 고정 근거를 보존하고 패키지 업데이트와 연결 계약을 따르세요. 이 경로는 이 패키지에 기록한 원인에 적용합니다. 출처가 누락되면 알리고 꾸미지 마세요.

<a name="authorization-lifecycle-a26--auth01"></a>

### 승인 수명 주기 (A26 / AUTH01)

`authorization`은 명시적으로 구성한 이벤트 객체입니다. 비어 있지 않은 과거 `authorization`이어도 단순 문자열은 거부합니다. 구버전 상태는 가져올 수 없습니다. 새 작업에는 현재 패키지, 현재 승인, 새 실행이 필요합니다. `interpretation`은 별도의 최상위 문자열입니다. 사용자의 정확한 인용을 문장 부호까지 보존하고 주 에이전트의 해석을 붙이지 마세요. 분리한 출처 필드 `source_message`는 이벤트의 인용과 출처 정보에 정확히 일치해야 합니다.

아래는 계속 요청 입력의 예입니다. 합성 ID 및 시각을 실제 관측으로 바꾸세요.

```json
{
  "authorization": {
    "event_id": "user-event-42",
    "kind": "explicit_goal_continuation",
    "exact_quote": "Continue this goal now.",
    "source_kind": "user_goal_continuation",
    "source_id": "user-message-42",
    "goal_id": "goal-7",
    "thread_id": "thread-3",
    "run_id": "run-5",
    "scope": {"kind": "objective", "id": "scope-5", "objective": "Deliver the authorized project change"},
    "observed_at": 1791230401,
    "source_created_at": 1791230401, "original_turn_id": "turn-42", "observed_turn_id": "turn-42"
  },
  "interpretation": "Main classified this source as immediate continuation of the matching objective.",
  "source_message": {
    "source_kind": "user_goal_continuation",
    "source_id": "user-message-42",
    "exact_quote": "Continue this goal now.",
    "source_created_at": 1791230401, "original_turn_id": "turn-42"
  },
  "app_goal_observation": {
    "goal_id": "goal-7", "thread_id": "thread-3", "status": "active",
    "source_kind": "get_goal", "source_id": "actual-goal-tool-receipt",
    "observed_at": 1791230402
  }
}
```

출처 종류는 `user_message` 또는 `user_goal_continuation`입니다. 식별자와 인용은 비어 있지 않은 문자열이어야 합니다. 이벤트 관측은 300초 뒤 만료되고 미래 시각일 수 없습니다. 이벤트 ID와 출처 메시지는 완료된 실행 사이에서도 두 번 사용할 수 없습니다. 메시지 식별자는 두 출처 종류에서 모두 채팅 ID와 출처 ID의 조합입니다. 이벤트 ID나 출처 종류를 바꿔도 같은 사용자 메시지를 재사용할 수 없습니다. 앱 목표 관측에는 일치하는 목표·채팅 ID, `get_goal` 출처, 비어 있지 않은 기록 ID, 이벤트 이후의 유한한 60초 이내 시각이 필요합니다. 본 작업 전에 최신 실제 목표 관측을 얻고 `app-goal`로 기록하세요. `task`와 `prepare`가 저장한 관측을 현재 시계와 승인 식별자에 비춰 재검사합니다. 60초는 허용되지만 61초, 미래 시각, 식별자 불일치는 상태 바이트를 바꾸지 않고 거부합니다. 사용량이나 목록을 갱신해도 앱 목표 근거는 갱신되지 않습니다. 이 데이터는 모두 **호출자가 제공한 근거**입니다. Python은 구조, 일치 여부, 최신성, 상태 전이 제약을 검사합니다. 공급자에게 연락하거나 대화 기록을 인증하거나 자연어를 분류하거나 호출 기록을 인증하거나 사용자가 실제로 인용문을 제공했음을 증명하지 않습니다. 주 에이전트가 실제 출처와 도구 기록을 확보·보존하고 이벤트 종류를 올바르게 분류해야 합니다. 같은 인용문을 두 번 꾸며도 일치 검사는 통과합니다. 일치 여부가 독립적 출처 확인을 대신할 수 없습니다.

| 이벤트 유형 | 새 활성화 | 이전 목표가 멈췄거나 중단 확정됨 | 작업 배정에 미치는 영향 |
|---|---|---|---|
| `explicit_task_authorization` | 별도 실행·범위, 일치하는 목표, 관측된 활성 앱 목표 | 재개 불가 | 새로 승인된 실행만 |
| `explicit_goal_continuation` | 활성 앱 목표 근거가 있으면 별도 실행·범위 허용 | 아래 검사를 모두 통과해야 재개 | 성공 후 새 작업 가능 |
| `future_goal_intent` | 거부 | 재개 거부 | 이전 작업 승인 불가 |
| `policy_change` | 거부 | 재개 거부 | 이전 작업 승인 불가 |
| `independent_report_request` | 별도의 `kind: report` 범위와 정확한 보고 목표만 허용 | 기존 중단 실행의 재개나 활성화 거부 | 별도 보고 실행만 허용. 기존 작업은 계속 중단됩니다. |
| `explicit_stop` | 거부 | 식별자와 범위 일치 시 `observe-authorization`으로 기록 | 새 task·prepare 즉시 차단 |

`observe-authorization`은 목표를 활성화하거나 재개하지 않고 미래 의도, 정책 변경, 별도 보고 요청, 지정 범위의 중단을 기록합니다. 현재 승인도 바꾸지 않습니다. 중단된 목표의 보고서는 별도 보조 프로젝트와 상태에서 실행합니다. 중단된 실행을 덮어써서 그 작업에 접근할 수 없습니다. `app-goal`은 별도로 최신 관측을 기록합니다. paused, blocked, stopped, complete의 관측은 활성 보조 프로그램의 작업을 차단합니다. 이후 active 관측만으로 사용자 재개를 확인할 수 없습니다. Codex UI 복구에는 먼저 중단 확정 후 비활성 관측이 필요합니다. 측정 만료 중단이 기록됐다면 대신 기존 승인 아래에서 `usage_recovery`를 씁니다. `status`는 보조 프로그램의 `status`와 `app_goal_observation`을 따로 반환합니다. 배정 프롬프트에는 승인 범위와 목표·채팅·실행 식별자가 들어갑니다.

직접 사용자 메시지로 재개하려면 stop과 halt보다 엄격히 나중에 관측한 새 `explicit_goal_continuation` 이벤트를 전달하세요. 저장된 모든 식별자와 정확한 범위가 일치해야 합니다. 중단 확정 후 실제 사용량과 실제 하위 목록을 먼저 읽습니다. 사용량은 최신이어야 하며 한도 여유가 임계값을 넘고 적응형 기한 안에 있어야 합니다. 목록은 최신이며 소유한 하위 에이전트 중 활성 또는 알 수 없는 상태가 없어야 합니다. 체크포인트 복원과 현재 파일 해시를 재검증하세요. 중단 확정 이후 그리고 계속 요청보다 이르지 않은 시각에 일치하는 앱 목표의 활성을 관측합니다. 저하 상태로 중단했으면 체크포인트를 고쳐야 합니다. 재개에 성공하면 이전 미완료 작업을 거부하고 새 배정을 허용합니다. 하위 에이전트를 암시적으로 다시 시작하지 않습니다. 승인이 누락됐거나 오래됐거나 재사용됐거나 잘못됐거나 계속 요청에 해당하지 않으면 상태 바이트를 바꾸지 않고 거부합니다.

사용자가 중단을 명시하면 주 에이전트는 본 작업과 새 배정을 즉시 중단합니다. 복구에 필요한 범위 안에서 해당 작성자 중단과 짧은 확인, 보존, 중단 확정만 수행하세요. 중단 중 새 계획이나 상세 인계 또는 복구 기반을 만들지 않습니다. 앱 관측은 보조 프로그램 상태 전이와 별도로 기록합니다. 보조 프로그램은 Codex 도구를 가로채지 않습니다. 출처 분류와 Codex 쪽 중단 규칙을 주 에이전트가 따릅니다. 임시 Python 테스트 외에도 A26에는 실제 Codex 계속·중단 기록과 무단 Codex 동작에 대한 독립 감사가 필요합니다.

`stop`은 배정을 차단하고 아직 쓰는 담당자에게 필요한 SAVE_ACK 요청을 반환합니다. 담당자마다 짧은 확인을 하나씩 받으세요. 최대 30초 후 응답하지 않은 해당 담당자는 필요하면 중단하고, 메모리에 저장되지 않은 내용이 남을 수 있다고 알립니다. 스냅샷 전에 디스크 쓰기가 멈췄는지 확인하세요. 보조 프로그램은 메시지를 보내거나 프로세스를 멈추거나 계속 조회하지 않습니다.

감시가 정상이 아니거나 `SAVE_AND_STOP`이 기록돼도 고정 후보에서 `stop`을 쓸 수 있습니다. 복구에 먼저 정상 측정을 요구하면 안 됩니다. 직접 `stop` → `snapshot` → `halt`와 복구 전용 배치에는 같은 허용 명령 목록을 사용합니다. 이 경로는 새 작업 승인, SAVE 해제, 비정상 실행 유지 기한 연장, 작업 재개를 허용하지 않습니다. `halt`는 계속 쓰기가 멈췄는지, 체크포인트 무결성과 해당 프로세스 종료를 검사합니다.

작성자의 쓰기가 멈췄다는 관측 이후 `snapshot`에 `files`(변경·생성·삭제된 모든 프로젝트 상대 경로), `next_action`, `writers_quiescent: true`를 전달합니다. 모든 작업에 배정된 경로는 자동으로 포함됩니다. 주 에이전트가 쓴 파일과 Git에서 추적하지 않는 파일을 명시적으로 포함하세요. 복사 중 파일 해시가 그대로여야 합니다. 매니페스트에 없거나 삭제된 경로와 상태 사본을 저장합니다. 새 내부 디렉터리에서 복원을 시험하고 해시를 검사합니다. 자격 증명은 업로드하지 않습니다. 복구할 수 있는 관련 외부 산출물은 해당 도구로 먼저 로컬에 저장해야 합니다.

호스트 도구로 이 실행에서 소유한 에이전트와 프로세스만 중단하세요. `halt`에 최신 `inventory`, `observed_at`, `owned_processes_stopped: true`, 실제 도구 관측의 `stop_evidence`를 전달합니다. 체크포인트와 현재 파일 해시를 다시 검사합니다. 스냅샷이나 복원이 실패하면 `degraded: true`와 `reason`, `next_action` 및 실제 중단 근거를 적습니다. 이때 검증된 복구라고 주장하지 마세요. `resume`은 위에 설명한 측정 만료 복구, 직접 계속 요청, 더 새로운 Codex UI 전이 중 하나와 모든 해당 검사를 요구합니다. 저하 상태로 중단했다면 먼저 체크포인트를 수정합니다. 초기화를 자동으로 활용해 재개하거나 Codex 목표 상태를 자동으로 바꾸지 마세요. 측정 복구는 이미 승인된 활성 목표만 복원합니다.

`restore`는 검증된 체크포인트를 프로젝트 밖의 새 경로에 복사합니다. 프로젝트 내용은 `files/` 아래에 두고 복구 메타데이터는 이 하위 트리 밖에 둡니다. 매니페스트에는 없어야 하는 경로가 기록됩니다. 사용 중인 프로젝트 파일을 삭제하거나 덮어쓰지 않습니다. 스냅샷을 지속적으로 기록한 뒤 현재와 이전의 정상 체크포인트를 보존하세요. 해당 실행이 소유한 오래된 디렉터리만 정리하고 링크는 거부하며 출처가 불명확한 내용은 보존합니다. `compact`에는 활성 하위 에이전트와 미완료 작업이 없고 검증된 스냅샷이 필요하며, 완료 작업의 기록을 제거합니다. `complete`는 결과를 전달한 실행을 닫습니다. 이후 작업에는 새 활성화가 필요합니다.

## 기계적 조율과 지속적인 작업 배정 기록 (N05)

`scripts/candidate.py <global pins/options> coordination --input <request.json>`은 표준 라이브러리의 모델 없는 어댑터입니다. 요청 형식은 `{ "batch_id": "unique_id", "steps": [{ "key": "unique_step", "command": "task", "payload": { ... } }], "seen": [] }`입니다. 최대 64단계를 순서대로 실행합니다. 워크플로 명령은 각각 검증, 상태 잠금, 기록을 수행하며 배치 전체는 의도적으로 원자적이지 않습니다. 독립 읽기에는 `read`와 정확한 프로젝트 상대 파일의 목록인 `payload.paths`를 사용합니다. 저널에는 읽은 텍스트, 바이트 수, SHA-256이 저장되고 없는 파일의 해시는 null입니다. 어댑터는 장애 요인, 실제 관측된 세션 식별자, 워크플로 소스 해시, 저널 경로, 단계별 결과, 결과 토큰을 담은 짧은 결정을 반환합니다. 원본 요청, 호출 기록, 결과는 `.agent-workflow-v1-1/runs/<run-id>/coordination/<batch_id>.json`에 있습니다. 변하지 않은 완료 결과를 숨기려면 이미 소비한 결과 토큰을 `seen`으로 전달하세요. Codex 도구 출력은 이 어댑터의 범위 밖입니다.

각 단계는 실행 전에 상태 해시와 함께 `pending`으로 기록합니다. 이후 별도로 이후 해시와 결과를 `applied`로 기록하거나, 오류와 이후 해시를 `failed`로 기록합니다. 상태 변경 뒤 결과를 적기 전에 프로세스가 실패하면 `pending`으로 남습니다. 배치를 다시 실행해도 다른 단계를 적용하지 않고 장애 요인을 반환합니다. 적용된 단계는 다시 실행하지 않습니다. 실패한 단계에서 배치를 멈추며 이전 결과를 보존합니다. 한 ID에 다른 요청을 재사용하거나 의도와 결과 근거를 지우지 마세요. 상태 바이트가 같다는 이유만으로 안전하게 재시도할 수 있다고 판단하지 마세요. 파일 스냅샷이나 복원 효과가 이미 발생했을 수 있습니다. 지속적인 저널과 현재 코어 상태를 조사하고 실제 외부 기록을 보존한 뒤, 알 수 없는 부수 효과를 명시적으로 확인하고 새 범위의 대조 배치를 사용하세요. 비정상 종료를 자동으로 성공 처리하지 않습니다. 저널 잠금과 코어 잠금은 각자의 기록을 보호합니다. 주 에이전트만 쓰며 다른 도구와 전역 트랜잭션을 만들지 않습니다. 오래된 잠금은 제거 전에 소유자를 확인합니다.

저널에 기록하는 Codex 작업 배정은 다음과 같습니다.

1. 배정 검사 시 실제 Codex 세션 목록을 얻어 `inventory`로 기록합니다. `prepare`는 평소의 정확한 Codex 인자와 `intent_id`를 반환합니다. 이 ID는 코어 작업에 지속적으로 예약됩니다.
2. 실제 Codex 도구를 호출하기 직전에 `id`와 `intent_id`로 `dispatch-start`를 호출합니다. 현재 승인·앱 관측, 사용량과 SAVE, 목록, 작업·입력 유효성, 배정된 쓰기 해시를 다시 검사합니다. 정확한 `collaboration.spawn_agent` 인자를 돌려주기 전에 `uncertain`을 기록합니다. 호출 시간 초과, 결과 누락, 다시 시작 시 중복 배정을 막습니다. 실제 호출 전에 비정상 종료돼도 결과는 불확실합니다. 해소하기 전에 실제 목록을 조사하세요. 직렬의 기존 `prepare`, Codex 호출, `record` API도 쓸 수 있지만 호출 전 불확실성 기록은 없습니다.
3. 주 에이전트가 지원 도구로 실제 `collaboration.spawn_agent`를 직접 호출합니다. Python이나 `functions.exec`에서는 호출하지 않습니다. 실제 결과를 보존하세요. 최신 목록을 `observation: { "source_kind": "collaboration.list_agents", "source_id": "caller-capture-correlation-id", "evidence_path": "operations/raw-native-inventory.json", "sha256": "<actual-file-hash>" }`로 기록합니다. 원본 출력은 정확히 이 프로젝트 상대 파일에 한 번 저장하고 상태와 저널에는 참조와 해시만 남깁니다. 경로와 해시 대신 직접 `receipt: <actual-native-output>`을 쓸 수도 있습니다. 이 방식은 상태와 저널에 원본 출력을 중복 저장합니다. 둘 중 하나만 사용하세요. Codex 출처 필드는 `dispatch-start`와 뒤늦게 확인한 성공을 대조할 때 필수입니다. 60초 유효 기간이나 ID와 상태 검사를 대신하지 않습니다. 코어는 매번 근거를 읽어 해시를 확인합니다. `native_inventory(raw)`는 지원하는 실제 `{agents:[{agent_name,agent_status}]}` 출력을 정규화합니다. `running`과 `idle`은 그대로이고, `interrupted`는 `stopped`, 정확한 형태 `{completed: <final text string>}`는 `done`이 됩니다. 알 수 없거나 잘못됐거나 모호하거나 중복된 항목은 거부합니다. 호출자가 정규화한 목록은 순서와 무관하게 원본에서 얻은 값과 같아야 합니다. 완료한 결과 전문은 근거 파일에 남습니다.
4. 불확실한 작업을 `id`, `evidence`, `no_owned_work_running: false`, 정확한 `submitted_arguments`, 실제 `session_id`와 `receipt`로 대조합니다. 관측한 실제 모델과 추론 강도는 선택입니다. 호출 기록은 `id`, `agent_id`, `session_id`, `task_name` 중 하나가 목록의 세션 식별자와 같은 객체여야 합니다. 그 세션은 남겨 둔 배정 의도보다 이르지 않은 최신 목록에 알려진 상태로 있어야 합니다. 준비한 인자와 변경 불가능한 입력도 계속 일치해야 하며 세션 재사용은 거부합니다. `Coordination.receipt(...)`는 이 전이를 시도하기 전에 실제 원시 기록을 저널에 씁니다. CLI 호출자도 같은 `reconcile` 단계를 보낼 수 있습니다. 누락, 만료, 잘못된 출처, 잘못된 형식, 식별자 불일치가 있는 근거로는 running 상태로 넘길 수 없습니다. 중단 도중 뒤늦게 발견된 세션은 보조 프로그램 상태 `stopping`으로 복구를 위해 기록합니다. 권한을 재개하거나 새 배정을 허용하지 않습니다. 입력의 무효화로 대조할 수 없다면 기록과 저널을 보존하고 실제 하위 에이전트를 Codex 도구로 중단합니다.
5. 실제 최신 목록에서 종료 상태를 확인한 뒤에만 승인 단계에서 완료를 기록합니다. 독립 검토와 산출물 해시 검사를 유지합니다. 종료나 복구 시 기존 검사에 따라 실제 목록을 다시 조회하세요. 해당 실행에 속한 작업 중 활성 상태나 미확인 상태가 없음을 확인했다면 기존 `reconcile`에 `no_owned_work_running: true`를 전달해 불확실한 작업을 거부합니다. 다시 실행하거나 호출 기록 없이 성공을 추정하지 않습니다.

보조 프로그램은 전달받은 형식, 출처 라벨, 최신성, 일관성을 검사합니다. 호출자, Codex 기록, 대화 기록을 인증하지 않습니다. 내부적으로 일관된 Codex 라벨을 붙인 합성 객체는 로컬에서 구별할 수 없습니다. 주 에이전트가 실제 Codex 도구 결과를 얻고 보존해야 합니다. 공급자가 기록 ID나 호출 ID를 주지 않으면 `observation.source_id`는 보존한 한 건의 원본 결과를 찾기 위해 주 에이전트가 생성한 상관관계 ID입니다. 호출자가 만들었다고 명시하며 공급자 발급 또는 인증 ID라고 하지 마세요. 실제 시작 결과의 에이전트·세션·작업 식별자는 그래도 일치해야 합니다. 기록의 식별자 확인과 메타데이터 인증은 별개입니다. Codex 쪽 준비, 시작, 기록은 원자적 동작이 아니며 어댑터는 Codex 도구나 그 출력을 가로채지 않습니다. 저널의 `source_pin`은 workflow.py와 coordination.py의 SHA-256을 담은 정규 맵의 해시입니다.

`collaboration.list_agents`는 이미 알고 있는 표준 작업 접두사를 지정하는 `path_prefix`를 지원합니다. 필요한 소유 그룹마다 검사 시점에 한 번 관측합니다. 루트가 불명확하면 먼저 목록을 조회합니다. 접두사로 검색해도 완료 에이전트의 전체 최종 결과가 반환될 수 있습니다. Codex 도구에 존재하지 않는 `compact`, `exclude_completed` 또는 출력 필터 스위치를 만들지 마세요. 로컬 저널 결과 토큰은 이미 전달한 보조 프로그램의 결과만 숨깁니다. 공급자 출력의 바이트가 필터링됐다는 근거가 아닙니다.

저장소 루트에서 `python -X utf8 -B -m unittest discover -s skills/agent-workflow-v1-1/tests -p test_candidate_coexistence.py -v`로 지원되는 소스와 준비된 패키지의 하위 프로세스 진입점, 검사된 배치, 수명 주기를 시험합니다. 직접 코어를 실행한 이전 테스트 기록은 후보의 준비 상태를 입증하지 않습니다. 두 경로에서 작업·입력을 같은 방법으로 고정하고 준비하며 합성 기록과 합성 종료 관측을 입력하고 승인을 지나 스냅샷을 검증하고 실행을 닫습니다. 테스트는 하위 프로세스 명령 수, 종료 코드, 실제 표준 출력·오류 바이트를 보고합니다. 이 값은 주 에이전트의 결정 경계를 모형화한 값이며 실제 모델 호출을 측정한 값이 아닙니다. 합성 기록과 콜백은 Codex 작업 배정을 증명하지 않습니다. 주 에이전트는 실제 도구 기록으로 직렬과 배치의 Codex 경로를 따로 측정해야 합니다. 타이밍과 임시 절대 경로 길이 및 직렬화에 따라 바이트 수가 바뀔 수 있습니다.

<a name="install-and-update"></a>

## 설치와 업데이트

`tooling/build-candidate.py`로 동일한 소스에서 같은 패키지 파일, ZIP, 외부 빌드 기록을 생성하세요. 지원되는 후보 `install --destination <explicit-directory>/agent-workflow-v1-1` 명령은 모든 바이트를 검증합니다. 기존 관리 대상의 내용이 같으면 다시 쓰지 않습니다. `--update`는 변경되지 않은 관리 대상 설치본을 교체하며, 편집됐거나 관리하지 않는 내용은 거부합니다. 배치 실패 시 이전 디렉터리를 트랜잭션으로 복원합니다. 업데이트가 성공하면 이전 패키지나 롤백 아카이브는 유지하지 않습니다. 정확한 명령과 신뢰 기준 처리는 [런타임 연결](coexistence.md)을 보세요.

암시적 스킬 선택은 꺼져 있습니다. 실행별로 고정한 소스 후보, 준비된 후보 또는 설치 후보 매핑이 실행 식별자입니다. 실행 중 매핑을 바꾸지 마세요. 감시 엔진, 역할, 지침은 `private/limit-watcher` 아래에서 관리 및 배포하고 고정 후보 진입점만 제어합니다. 후보 업데이트에는 새 승인 실행이 필요합니다. 기존 출처 기록을 이전하거나 다시 연결하지 않습니다. 패키지 빌드나 설치만으로 AGWF가 활성화되거나 에이전트가 등록되지 않습니다. 프로젝트 준비를 위해 사용자가 AGWF를 명시적으로 호출하면 그 범위에서 위의 시작 절차를 수행합니다. 주 클라이언트 모델은 사용자가 선택합니다.
