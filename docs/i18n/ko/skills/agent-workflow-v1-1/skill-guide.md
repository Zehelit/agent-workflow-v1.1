# agent-workflow-v1.1

사용자가 이 실행에서 agent-workflow-v1.1을 명시적으로 선택한 경우에만 사용합니다. 암시적 호출은 꺼져 있습니다. 현재 명시적 호출에 따라 주 에이전트는 준비와 작은 작업을 포함해 승인된 범위의 AGWF를 같은 턴에 시작합니다. 이전에 꺼둔 적이 있어도 해당 범위의 실행은 다시 활성화할 수 있습니다. 과거의 선택이나 다른 세션의 선택에는 그런 효력이 없습니다. 스킬을 논의, 인용, 검사, 유지보수한다고 해서 중단된 프로젝트 작업이 재개되지는 않습니다. 주 채팅이 조율을 맡으며 결과 전달, 상태 쓰기, 실제 작업 배정을 책임집니다. 주 에이전트의 모델과 추론 강도는 사용자가 클라이언트에서 선택합니다. 스킬은 둘 다 지정하지 않습니다. 시작 뒤 작은 작업은 주 에이전트가 수행하세요. 팀은 선택할 수 있고 시작과 감시는 필수입니다.

<a name="required-startup-on-explicit-invocation"></a>

## 명시적 호출 시 시작 절차

본격적인 조사, 프로젝트 변경, 테스트, 위임 전에 새 Codex 사용량 기록을 얻고 고정 후보로 시작하세요. 근거가 확보됐다면 승인된 `workflow activate` 또는 `bind-active-goal`을 사용합니다. 사용자가 준비로 범위를 한정했거나 Codex 목표 생성을 금지했거나 활성 목표가 없으면 [운영 안내서](references/operations.md)의 수동 절차로 내장 감시 프로세스를 시작합니다. 승인된 범위를 지키고 명시적 승인 없이 목표를 만들지 마세요. 스킬을 로드하거나 선택기를 켜거나 사용량을 한 번 읽는 것만으로 시작이 완료되지 않습니다.

실제로 시작됐는지 확인하세요. 선택한 실행과 실행 세대에 대해 최신 정상 측정값이 있고, 해당 실행이 소유하는 감시 프로세스가 동작해야 합니다. 전체 워크플로라면 활성 상태도 확인하세요. 본 작업 전에 시작 결과를 알리세요. 같은 승인 범위의 정상 실행을 사용할 수 있다면 프로세스를 중복으로 띄우지 말고 재사용하세요. 중단 이후 명시적 호출이 다시 들어오면 기존 재개 절차와 새 실행 세대를 승인할 수 있습니다. 실제 사용자 이벤트와 모든 복구 검사 정보를 보존하세요.

시작이 거부되거나 근거가 없거나 한도가 `SAVE_AND_STOP`을 요구하면 즉시 구체적 원인을 알리고 필요한 복구만 수행하세요. 주 에이전트가 요청 작업을 조용히 직접 진행하면 안 됩니다. 이후 중단 지시가 우선합니다. 중단 상태에서 스킬을 확인하거나 업데이트해도 이전 작업이 재개되지는 않습니다.

워크플로 명령, 조율, 내장 사용량 감시에는 고정 진입점 `scripts/candidate.py`를 사용하세요. 승인된 매니페스트 해시로 터미널에서도 직접 실행할 수 있습니다. 직접 실행의 전제 조건으로 스킬 호출이나 감시 실행이 필요하지 않습니다. 코어 CLI 직접 실행은 거부됩니다. 외부 신뢰 기준과 실행 격리는 [런타임 연결](references/coexistence.md)에, 실행 시작 절차는 [운영 안내서](references/operations.md)에 있습니다. 모델 설정의 출처는 역할 TOML 및 `private/limit-watcher/role.json`입니다. 감시 엔진, 지침, 역할은 이 스킬 내부에서 유지보수, 패키징, 검사됩니다. 별도의 감시 스킬이나 실행 도구는 없습니다.

<a name="role-skills-and-memory"></a>

## 역할 스킬과 메모리

정의된 하위 에이전트에는 각각 `SKILL.md`, `MEMORY.md`가 있습니다. coordinator, architect, implementer, researcher, verifier는 `roles/<role>/`에, limit_watcher는 `private/limit-watcher/`에 있습니다. 역할 정의가 해당 문서를 명시적으로 가리킵니다. 준비한 작업에는 해당 역할의 스킬과 메모리만 포함하며, 문서가 없거나 비어 있으면 로드를 거부합니다. 임시 전문 담당자는 기본 역할의 문서와 작업에 필요한 분야별 지침을 받습니다.

역할 스킬은 각각 명시적으로만 호출할 수 있습니다. 역할 스킬은 내부 배정 지침입니다. 준비된 역할 배정과 실제 모델·추론 강도 일치 근거 없이 직접 선택했다면 무엇이 빠졌는지 알리고 멈춥니다. 역할 스킬이 AGWF를 활성화하거나 감시 프로세스를 시작하지 않습니다. 워크플로를 끄려면 스킬 항목 일곱 개를 모두 끄고 해당 프로세스를 종료해야 합니다. 업데이트가 그 항목을 다시 켜지 않습니다.

역할 메모리는 계속 참고할 자료입니다. 권한을 부여하거나 현재 프로젝트의 근거를 대신하지 않습니다. 과거 관측을 꾸며서 시작하지 마세요. 메모리 추가 제안은 주 에이전트에게 반환합니다. 주 에이전트가 검토해 실행 사이에 관리 문서에 반영합니다. 역할 문서는 패키지 매니페스트에 포함되므로 메모리 변경에도 일반 패키지 업데이트와 새 실행 연결 절차가 적용됩니다. 작업 중 설치된 스킬을 수정하지 마세요.

<a name="integrated-limit-watcher"></a>

## 내장 사용량 감시

고정 후보를 통해 승인된 `workflow activate` 또는 `bind-active-goal`을 실행하면 모델을 쓰지 않는 내장 감시 프로세스가 자동으로 시작됩니다. 활성화 전에 기존 Codex 연결에서 실제 `mcp__codex_app__get_usage_limits` 측정 기록을 받아 `--usage-input`으로 전달하세요. [Codex 사용량 기록 형식](references/native-usage.md)을 따르세요. 감시 프로세스는 Codex 애플리케이션 서버를 시작하거나 PATH에서 CLI를 고르거나 다른 전송 경로에 접속하지 않습니다. 후보 프로그램은 활성 상태를 기록하기 전에 최근 정상 측정값을 검증합니다. 기록이 없거나 만료되면 활성화를 거부합니다. `resume`에도 같은 수준의 새 기록과 새 실행 세대가 필요합니다. `usage_receipt_expired`가 기록된 중단은 아래 기술 복구를 따릅니다. 그 밖의 중단에는 직접적인 사용자 계속 요청 또는 허용되는 Codex 목표 전이가 필요합니다.

주 에이전트는 승인된 작업 중 적응형 300/120/60/30초 기한까지 Codex 기록을 갱신합니다. 백그라운드 Python 프로세스는 받은 측정값을 검증하고 최신 데이터가 없으면 작업을 차단합니다. 호스트 도구를 직접 호출할 수는 없습니다. 파일을 다시 읽어도 관측 시각은 갱신되지 않습니다. 활성 명령은 600초의 실행 유지 기한을 연장합니다. 감시 상태가 정상이 아니면 새로운 작업을 차단하고 복구 명령은 계속 사용할 수 있습니다. `complete`와 `halt`는 해당 실행의 작업 프로세스를 중단하고 종료를 확인합니다. 상태 신호는 패키지 해시를 계산하지 않고 실행과 실행 세대의 소유권을 확인합니다. 전체 의존성 검사는 명령과 측정 경계에서 합니다. 작업 경계마다 `workflow status`를 사용하세요. 조용한 채팅은 데이터나 기한을 갱신하지 않습니다. 명시적 선택을 받으면 주 에이전트가 시작을 시행하고 검증해야 합니다. 클라이언트에 자동 실행 연결은 없습니다. 수동 `watcher start/ingest/status/renew/stop`도 동일한 측정과 승인 조건을 따릅니다.

잔여량이 25%일 때 완료한 작업의 검증된 체크포인트를 준비하세요. 20%이거나 조기 복구 신호가 오면 새 작업을 중단하고 쓰기 중인 담당자에게서 짧은 확인을 받은 뒤 필요한 파일을 검증하고 해당 실행의 프로세스만 중단하세요. 사용량이 없으면 알 수 없는 상태입니다. 한 번만 다시 시도한 뒤 저장하고 멈추세요. `SAVE_AND_STOP`은 다른 에이전트를 기다리지 않고 주 에이전트가 즉시 조치해야 합니다. 측정값 만료는 기술적 중단이며, 한도 소진이나 권한 철회의 근거는 아닙니다. 저장과 중단 확정 뒤 원인이 `usage_receipt_expired`로 기록되었고 같은 Codex 목표가 계속 승인돼 있고 활성 상태라면, `resume`과 `usage_recovery: true`로 재개할 수 있습니다. 새 실제 측정 기록, 같은 목표와 세션 목록의 새 관측, 변경되지 않은 검증된 체크포인트, 해당 프로세스 종료 확인이 필요합니다. 후보 프로그램은 `halt`에서 실제 감시 원인을 기록합니다. 이 경로에서는 한도, 조기 중단, 다른 실패, 사용자의 명시적 중단, 비활성 목표를 거부합니다. 근거가 확보되면 복구를 진행하세요. 측정 만료나 일시 정지 상태 미관측만을 이유로 새 계속 요청의 타이핑을 요구하지 마세요. 만료만을 이유로 Codex 목표를 `blocked`로 바꾸지 말고 목표 도구의 기준을 따르세요. 복원하는 대상은 감시 프로세스와 보조 프로그램이며 목표 상태를 바꾸지 않습니다. 사용자 인용이나 UI 이벤트를 꾸미지도 않습니다. 다른 중단에는 개별 재개 조건이 그대로 적용됩니다. 초기화만으로 자동 재개하거나 Codex 목표 상태를 자동 변경하지 마세요. 주간 구간 예외에는 사용자의 실제 발언과 유효 기간이 필요합니다. 측정에는 두 구간을 모두 남깁니다. 복구 판단이 모호한 경우에만 내장 `limit_watcher`를 정확히 `gpt-6.1-terra`와 `medium`으로 사용할 수 있습니다. 해당 설정을 쓸 수 없다면 누락을 보고하세요. [운영](references/operations.md)과 [감시 역할](private/limit-watcher/limit_watcher.md)을 참조하세요.

[컨텍스트 선택과 승인 규칙](references/context.md)으로 필요한 현재 상태만 인계하세요. 원래 승인 시각, 해시로 고정한 근거 참조, 검토자의 반대 근거를 보존하세요. 요약이 자체적으로 배정을 승인하거나 캐시 효과를 보장하지 않습니다. Codex 실행 완료와 독립 산출물 승인은 각각 버전 관리되는 별도 관측입니다. 중대한 결과의 독립 검토에 앞서 모델 없는 작성자 검사를 수행하세요.

하위 에이전트에는 목표, 필요한 입력, 허용된 쓰기 경로, 승인 기준을 제공하세요. 주 대화를 복제하지 않고 새 컨텍스트로 시작하세요. 구현 세션은 frontend, backend, editor, data_analysis처럼 실제 맡은 일에 맞춰 이름을 정하세요. 영구적인 분야 역할을 만들기 전에 관련된 기존 프로젝트 스킬을 활용하세요. 전문 작업에는 알맞은 기본 역할을 바탕으로 임시 담당자를 지정하고 정확한 이름, 분야 지침, 필요한 출처와 도구, 승인 기준을 전달하세요. 기존 분야 역할이나 사용자의 별도 호출은 필요하지 않습니다.

조사 담당자가 근거를 모아 정리하고 구현 담당자는 설계, 구현, 수정을 합니다. 검토자는 중요한 결과를 독립 확인합니다. 아키텍트는 비용이 큰 설계 선택이나 기술적 의견 차이를 해결합니다. 모든 작업에 관여하는 것은 아닙니다. 반복 가능한 기계 작업에는 스크립트를 사용합니다. 적절한 기존 스크립트를 먼저 쓰고 반복성이나 안정성 때문에 필요할 때는 프로젝트 내에 스크립트를 만들어 검증하고 재사용하세요. 작업에 따른 에이전트 판단이며 유휴 상태에서도 도는 스케줄러가 아닙니다. 고정된 Admin이나 Executor 계층은 없습니다.

파일마다 작성자 한 명만 두세요. 전문 담당자는 공유 인터페이스를 변경하기 전에 합의합니다. 보안, 인증, 데이터 손실 가능성, 공유 API, 넓은 동작 변경은 독립 검증하세요. 범위가 좁고 되돌릴 수 있는 작업은 주 에이전트가 검증할 수 있습니다. 원본 로그를 넘기기보다는 결론, 변경 경로, 근거를 반환하세요.

현재 사용자의 승인과 프로젝트 제약을 지키세요. 중단 지시가 오면 명시적으로 계속하기 전까지 추가 배정은 취소합니다. 현재 작업과 지속적으로 필요한 결정만 보관하세요. 복구에 필요하지 않다는 점이 확정된 뒤에만 자신이 만든 임시 자료를 지웁니다. 임의의 메시지 길이 제한이나 필수 회의는 없습니다.

보조 프로그램은 자신을 통과한 동작을 검증합니다. Codex 도구를 가로채거나 프로세스를 자동으로 중단하지 않습니다. 반환된 도구 호출을 실행하고 결과를 기록하고 실제 실행 목록을 조사하는 일은 주 에이전트가 맡습니다. 메타데이터 없이 요청한 모델을 실제 동작한 모델로 발표하지 마세요.

<a name="coordination"></a>

## 조율

서로 의존하는 전문 영역의 큰 작업을 배정하기 전에 `coordinator` 하위 에이전트에 작업 분할, 의존 관계, 전문 담당자 선택, 파일 소유권 제안, 승인 기준을 요청하세요. 범위가 크게 바뀌거나 담당자 결과 사이의 충돌이 해결되지 않거나 반복 실패로 새 계획이 필요할 때도 요청합니다. 작고 독립적인 작업 및 일상적인 진행 확인은 주 에이전트가 맡습니다.

목표, 현재 제약, 확인 내용, 관련 출처의 위치를 새 컨텍스트로 보내세요. 조율 담당자는 읽기 전용 계획을 반환하며 에이전트를 시작하거나 워크플로에 쓰지 않습니다. 주 에이전트가 사용자 제약과 실행 가능성을 확인하고 승인된 작업을 기록한 뒤 계획을 중복 작성하지 않고 실행합니다. 계획에 의존하는 작업은 `depends_on`으로 승인된 조율 작업에 연결하세요. 슬롯이나 파일 범위의 사소한 조정은 주 에이전트가 맡고, 중요한 전략 변경만 조율 담당자에게 돌려보내세요. 아키텍트는 기술 설계를 결정하고 조율 담당자는 작업 조직을 결정합니다. 끝난 세션을 기다리지 말고 필요하면 새 범위의 조율 작업을 사용하세요. 정확한 모델이나 강도가 없다면 알리고 계획에 의존하는 작업을 보류하세요. 독립적으로 승인된 작업은 계속할 수 있습니다. 복구는 계획 담당자를 기다리지 않습니다.

## 사용자 모델 정책 (2026년 10월 27일)

워크플로 역할에는 `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6.1-terra`만 사용할 수 있습니다. 추론 강도는 최소 `medium`이어야 하며 `none`, `minimal`, `low`는 모든 역할에서 금지됩니다. 역할 파일이 모델과 기본 강도를 지정합니다. 대체 모델이나 자동 전환은 허용되지 않습니다. 폐기한 `astra_coordinator` 역할을 되살리지 마세요. 내장 `limit_watcher`는 `gpt-6.1-terra`와 `medium`만 사용합니다. 주 클라이언트의 모델과 강도는 사용자가 고릅니다. 이 스킬이 선택하거나 바꾸지 않습니다.
